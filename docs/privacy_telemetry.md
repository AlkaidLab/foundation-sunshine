# Usage statistics, error reports and what leaves your computer

Foundation Sunshine sends a small amount of data to the developers' own server, `https://api.alkaidlab.com`, so that they can find and fix stutter and crashes faster, see which features are used and decide what to improve first. This page says exactly what is sent, when, and how to turn it off.
No script of Google or any other third party is loaded by the Web UI or the control panel. Nothing is sent to a third-party analytics service by a client.

## The log that goes with a crash report or a feedback report

When the host crashes, or when you send feedback from the Web UI or the control panel, the report is sent together with the log of that run of the program (the file `sunshine.log`). The log is text the program writes about itself; it can contain your user name, the name of your computer, folder paths, IP and MAC addresses, device serial numbers, tokens, pairing PINs, Wi-Fi names and game account names, so it is made anonymous on your computer before it is sent: those are removed (an address becomes a placeholder such as `<ip#1>`, the same address the same placeholder, so lines can still be matched); times, levels, components, error codes, numbers, versions and GPU and driver names stay. The service checks the first and last part again and refuses the whole log if it finds personal data. The log is kept for 90 days, in a private repository, and read by the developers only. Two cases, kept apart. **The log of a crash report** goes only when error reports are on. **The log of a feedback report you write yourself** is attached by the host when it receives the report, and pressing Send is your consent for that one send: the error-reports switch does not decide about it, and the feedback panel says so in one line and lets you look at what will be sent before you press Send. If the log cannot be read or uploaded, the feedback is still sent, without the log (the panel says so in its preview). When both switches are off, no install id is made or recovered for the report: it goes with a random one-time id of its own, used for the log and the report only, and the server does not count it as activity, a session or an install.

## Two choices, both on until you turn them off

| Choice | What it covers | Config key |
| --- | --- | --- |
| Usage statistics | counts of what is used, numbers about how streams perform and how smooth the pages feel, and a rough description of the computer (the `usage` and `experience` events below) | `telemetry_consent` (`on` / `off`) |
| Error reports | an error record with personal details removed: what failed and where, and how installs and updates ended (the `error` events below, and crash reports) | `telemetry_errors` (`on` / `off`) |

One exception to "off means nothing is sent": a feedback report you write and send yourself, and its log, go out whatever the error-reports switch says. Pressing Send is your consent for that one report; the automatic error records and crash reports still follow the switch.

Both are on by default; the first run says so once and asks nothing. Turn them off in the control panel or the Web UI under **About › Privacy**, or by setting the key in `sunshine.conf`. The host applies the choice at once: the events of an off kind that were waiting (in memory and on disk) are deleted, and nothing of that kind is kept or sent afterwards. A feedback report that was sent on purpose and is still waiting is not deleted: it is the person's own and goes out when it can, with the identity it was built with. When both are off the install ID is deleted as well and nothing identifies this install.
A person who answered *off* to the earlier single question keeps *off* for error reports until they turn it on.

## When you turn a choice off

Each time a choice is turned off (from on to off) the host sends **one** small record per product, and then nothing more of that kind until the choice is turned on again: which choice was turned off (usage statistics or error reports), the product (the host, and the control panel or the Web UI if they have talked to the host) and its version, with the same anonymous installation number that earlier batches carried and a fresh random session number. The batch holds nothing else about the computer: no system, architecture, graphics vendor or language. It lets the developers tell "this person turned it off" from "something is broken on our side" and count how many installations did; it is not counted as use. If the computer is offline at that moment the record waits on the computer and is sent later (it is tried for two weeks at most, then dropped). A host that starts with a choice already off, for the first time, sends nothing. If the choice is turned on and off again, another record is sent; a record that is still waiting for the first one is not sent twice. When both choices are off the installation number is deleted from the computer once the records are saved; until a record has been sent or has expired, the number is kept inside the waiting record and nowhere else.

The same practice is used by Mozilla Glean (the `deletion-request` ping sent once when upload is disabled) and by Firefox's data collection settings; this record carries less than those pings.

## Who sends what

The host is the only sender. The Web UI and the control panel hand their events to the host they belong to (`POST /api/telemetry/events`); the host checks them against the same allow-list, applies the two choices again, adds the identity and sends everything in batches. A browser behind a content blocker, or a network that cannot reach Google, therefore makes no difference.

## The events

Every event is a name and a few fixed words or numbers. Names that are not on this list, and properties that are not listed for a name, are dropped before anything is kept.

| Event | Properties |
| --- | --- |
| `app_start` | cold start (yes/no), start time in ms, update source (`mirror`, `github`, `other`) |
| `app_exit` | seconds the host ran |
| `stream_start`, `stream_end` | client kind (a fixed word such as `moonlight-macos`), client OS, video codec, width, height, frame rate, HDR, audio codec, transport, kind of application (`desktop`, `bigscreen`, `sparxie`, `steam`, `other`) and, for a Sparxie application, its game as a catalogue word such as `genshin`; the end adds the length in seconds and how it ended (`normal`, `error`, `timeout`, `kicked`) |
| `stream_quality` (one per stream) | frame rate (typical and low end), share of dropped frames, encode and capture time (typical and 95th percentile), network round trip, packet loss, bitrate, reconnects, stalls |
| `stream_health` (about one per hour of streaming) | for every stream: how many 60-second windows there were and how many were over a fixed bound for each of the host processing time, encode, capture, convert and send time, send backlog and frame-interval jitter; counts of frames, key-frame and reference-invalidation requests from the client, queue clears and dropped frames; packet loss, round trip, bitrate target and measured; the stream's codec, resolution, frame rate, HDR, transport, client kind and OS, bitrate band, encoder, capture method and the driver version of the graphics adapter (digits and dots). For a share of the streams (set by the server, ten percent unless a new version is being watched) also a histogram of each statistic over the windows |
| `stream_anomaly` | one of the fixed codes `XP_QUEUE_FLUSH`, `XP_SEND_BACKLOG`, `XP_HOST_LATENCY`, `XP_ENCODE_OVER`, `XP_CAPTURE_STALL`, `XP_FRAME_SKIP`, `XP_IDR_STORM`, `XP_LOSS_BURST`, `XP_RTT_HIGH`, `XP_BITRATE_SHORT`, with the measured number, its bound, a count and the stream's dimensions |
| `stream_regress` | the name of one statistic, its value over the earlier windows of this installation and over the latest ones. Your installation keeps a rolling average of these statistics in the telemetry folder; nothing else of it is sent |
| `startup` | host start time, time to the first frame of a stream |
| `feature_used` | a fixed word naming a feature (`stream.hdr`, `web.apps_saved`, …) |
| `setting_changed` | which of a short list of settings changed (encoder, capture, codec modes, frame-rate and bitrate buckets, …) and the new value as a fixed word or a range such as `8000-15000` |
| `panel_page` | the page and the time until its first frame |
| `page_vitals` | how smooth a page of the panel or the Web UI is, once per page and send (when the page is hidden, and every 15 minutes in a long session): for eight fixed ranges each, how many visits fell into them for the largest content paint, the response to presses, layout shifts, the longest busy frame, the first paint, the time until the page says it can be used and the memory of the page; the number of busy frames and their total time; how many frames of a scroll or an animation took up to 17, 34, 50 ms or longer; the seconds the page was in view. No trace of single events, no text |
| `api_latency` | how quickly the host answered the page: for each endpoint word (the path without numbers and ids) the number of calls, failed calls, timeouts and eight latency ranges |
| `update_result` | one finished step of an update: where the update came from (`mirror`, `github`, `manual`, `other`), the step (`check`, `download`, `verify`, `apply`, `restart`), ok or failed, for a failure a class of the reason (network, HTTP 4xx or 5xx, checksum, disk, permission, cancelled, other), the version it came from and went to, the duration. It follows the error-reports choice. The text of an error is never sent |
| `install_result`, `install_summary` | what the installer reports: for each component of an installation, upgrade, repair or removal (`host`, `vdd`, `gamepad`, `usbip`, …) the step, ok or failed, the exit code, whether a restart is needed, the version it came from, the duration; and for the run: ok, failed, cancelled or incomplete (it started and never finished). The installer writes a small journal in `<config folder>/telemetry`; the host reads it at its next start, sends it and deletes it. It follows the error-reports choice |
| `svc_lifecycle` | what the service did with the core since the last start of the host: how many cores it started or took over, how many extra ones it ended, how many ended without being asked and how many of those soon after a take-over, and the causes of restarts. The service leaves a small file of numbers and fixed words in `<config folder>/telemetry`; the host reads it at its next start, sends the counts and deletes it |
| `startup_timing` | the time until the interface can be used: from the start of the service to the web interface of the core, and from the opening of a page to its ready mark, in milliseconds, and whether it was slow (above 15 s or well above this installation's own usual time, which is kept in the telemetry folder) |
| `host_anomaly` | one of the fixed codes `XP_SVC_CORE_RESTART` (the core ended without being asked and was started again) and `XP_SLOW_READY`, with the measured time, its bound, a count, the cause as a fixed word and, for a core exit, the exit code |
| `device_facts` | coarse facts about the computer, when they are new or have changed (at most once a day): graphics vendor and driver version (digits and dots), the Windows build number, the number of screens, the highest refresh rate (snapped to a standard rate), whether the network adapter in use is wired or wireless and its speed class (`lt_1g`, `1g`, `2_5g`, `5g`, `10g`, `gt_10g`). No device name, serial number or address |
| `user_report` | a report you write in the error dialog: a category (bug, performance, compatibility, suggestion, other), the product and page, an error code, and one message made of your title, your description and a short summary of the error (cleaned, at most 2000 characters). Pressing Send is the consent for this one report, so it goes whatever the error-reports switch says; the automatic reports still follow the switch. It may carry a contact you chose to leave (one line, at most 200 characters, not cleaned): only the developers see it, in the one issue of this report, and it is not part of any summary or statistic. It may also carry one screenshot you added (optional; the window capture the panel took, or a picture you chose, pasted or dropped; at most 700 KB). You see it first and can remove it or cover places in it. The host checks it, uploads it to the developers' private storage with its metadata removed, and it appears only in the one issue of this report. The places of the window that show addresses, names, PINs, passwords and CDKs are covered automatically; a picture you choose yourself is not, and the panel says so. The full stack stays on your computer; the run log goes with it as described above |
| `error_report` | an error with its place: component, language, a fingerprint, an error code, severity, the place (a file in our own source tree and a line, or a module and an offset, or a page file name; never a path of your computer), up to 32 stack frames of the same shapes, up to 50 actions you took just before (ids of our own, no text) and the last up to 40 lines (200 characters each) of the component's own log. The first report of an error on each (UTC) day leaves at once with all of it; the same error again that day is only counted and leaves as one count a day, without stack, actions or log; at most 20 reports an hour. It follows the error-reports choice |
| `opt_out` | which choice was turned off: `usage` or `errors`; the product and version are the ones of every batch. Sent each time the choice is turned off, once per product, by the host itself (a page cannot send it) |
| `wer_event` | a fault of the virtual display driver that Windows wrote to the Application log: that it happened, the module (only the driver's own file), the exception code and the offset. No stack, and nothing of any other program. It follows the error-reports choice |
| `error` | component, code, severity and count. Native host records add a source filename and line, or a fixed logger identifier. The code groups the fixed parts of a [log template](error-event-grouping.md). The record excludes the log message, template and argument values. |
| `log_summary` | hourly count of warnings, errors and fatal errors by host component. |

The list of events and properties is the code in `src/telemetry/events.cpp`; the tests in `tests/unit/test_telemetry.cpp` check it. **About › Privacy** explains what is sent and what is not for each switch and opens "See what will be sent": the records waiting for the next send together with the fields every batch carries, exactly as they leave (`GET /api/telemetry/preview`); the counters are at `GET /api/telemetry/status`. The complete list of fields, with the code that sends each, why it is needed, how personal details are removed and how long it is kept, is [privacy-data-inventory.md](privacy-data-inventory.md) ([中文](privacy-data-inventory.zh.md)).

With every batch go: the version, the update channel, the operating system and its version, the CPU architecture, the GPU vendor (`nvidia`, `amd`, `intel`), the language, and two random numbers (below).

## Log excerpts after a serious stream problem

Only while **error reports** are on: when a stream has a serious problem (the send queue was cleared, or a frame left much too late), the host sends the last two minutes of its own log, six times a day by default (the server can change that, up to ten) and with at least ten minutes between two (the first of a run is not held back by that gap). Each line is cleaned with the same rules as the rest (names, paths, addresses, e-mail addresses, keys), text between double quotes, brackets or braces (where a log line names a game, an application or a device) and single-quoted names are dropped (a short bracket that only holds a code, such as `[E12]`, stays), your computer name and account name are removed wherever they appear, and the time of each line is the number of seconds before the problem, not the clock. The server cleans it again and keeps it as a private file for 90 days, like a crash dump. The server can lower these numbers or switch them off.

## What is never sent

Names; text you typed (apart from the report you write yourself and the cleaned log lines listed in the paragraph above); the name of your computer, your account, your devices or your clients; file paths; IP or MAC addresses; the titles of your games and applications (a game is at most a catalogue word such as `genshin`), apart from what a cleaned log line happens to say. An error event carries a code, never the text of the error: a log line or an exception message can hold what a person chose or typed.

Text leaves in four places only, and the last three only while **error reports** are on (a feedback report and its log are sent when you press Send, whatever the switch says). The report you write yourself (`user_report`), after the panel has shown you what leaves; it is cleaned in your browser, again in the host and again on the server, and cut to 2000 characters; a contact you leave with it is the one text that is not cleaned. The anonymised program log that goes with a crash report or a feedback report (`user_report.log_ref`; see the program log section). The log excerpt after a serious stream problem (above): lines of the host's own log. And the last up to 40 lines (200 characters each) of a component's own log that goes with the first report of an error (`error_report.log`). The program log is anonymised with the rules in the program log section (user and computer names, user segments of paths, IP and MAC addresses, e-mail, serial numbers, tokens, PINs, Wi-Fi names, game account names). The log excerpt and the component log lines are cleaned by the host with the log rules (names, folders, addresses including IPv6, e-mail addresses, keys; text between quotes, brackets and braces dropped; the component anonymises its own lines first). All of them stay lines of text, not a fixed list of words, so what a log line happens to say after that cleaning is sent. An error report also carries the place of the error (a file in our own source tree and a line, or a module and an offset; never a path of your computer) and the last 50 actions as ids of our own (pages opened, marked buttons, settings, stream start and stop; no text). The actions are not recorded while error reports are off, and what was held back when you turn them off is deleted.
The server keeps only the country code of the connection (from Cloudflare), not the address.

## Identity

`install_id` is a random UUID (version 4, RFC 9562), made once for this install and kept in `<config folder>/telemetry/install_id`. It is not derived from your hardware, name or account. `session_id` is a new random UUID at every start. Neither can be traced back to you by itself. Turning both choices off deletes the install ID; turning one on again makes a new one.
`GET /api/telemetry/identity` hands the install ID to the control panel and the crash reporter, and answers 403 while both choices are off.

## Sending, offline and limits


Serious things are sent first and are the last to be given up. Every event has one of three priorities: 0 for user reports, fatal errors, the first report of an error, serious stream problems and the per-stream summary; 1 for further reports of a known error and smaller problems; 2 for usage and performance detail. Three kinds of record must arrive and are never dropped to make room for anything else: crash reports, error reports (the first of an error each day, fatal errors, failed installs and updates) and feedback you sent. They are kept on disk and sent again, also after a restart, until the service has them or the room runs out (a crash report: at most 20 and 200 MB together, 30 days; error reports and feedback in the queue below, each with a bound of its own); feedback is the last to be given up, and they are sent as soon as the service takes them. When the queue on disk is full, priority 2 is dropped first, then 1, then the other priority 0 records, then error reports, and feedback last. When the server asks the clients to wait, priority 1 and 2 wait, and priority 0 leaves once per wait, with repeated events merged into one with a count.
Events wait in memory and are written to `<config folder>/telemetry/queue` (at most 100 files and 1 MB; the oldest go first), in batches of at most 500 events and 256 KB. Error reports and feedback are sent at once, in requests of their own. All other records (usage, performance, stream summaries) are sent once a day, at a moment of the (UTC) day that follows from the install ID, so the installs do not all report at midnight; a computer that was off at that moment reports soon after it is switched on. Of those, the sampled records (usage, performance and the per-stream summaries) are only sent by a sample of the installs (one in ten unless the server says otherwise); the failure record of that group (a stream that failed to start) is not sampled and leaves with the daily share of every install; a driver fault and a failed install or update are error reports and are sent at once: the batches of an install in the sample carry its weight (`sample_weight`, 10 for one in ten) so the service can count the others; an install outside the sample sends none of the sampled records, and its error reports and feedback are never sampled. A failure waits 30 seconds, then doubles up to one hour, and a crash report waits 15 minutes doubling to four hours; the server's `Retry-After` is obeyed; every wait is lengthened by a random share of up to a fifth (a quarter for crash reports). At most 15 requests a minute are made. Sending runs on its own thread and never makes a stream wait.
The endpoint can be changed with `telemetry_endpoint` (for a test server).

## What the server does with it

It stores per-install records (so that daily, weekly and monthly users can be counted) and the numbers above for reports to the developers. Events older than a week or from the future are given the time of arrival. The server drops anything not on the list.

## Crash reports

A crash report is a small description (the module file name and address where it happened, the error code, the version) and, when error reports are on, a dump of the crash. The dump is the smallest that still shows the call stack: no heap, no data segments, no handle data, only the pointer-sized values of each stack, with module paths filtered. Before it is sent, the account name in any `\\Users\\`, `/Users/` or `/home/` path and the user and computer names are overwritten in place. The Panel and `sparxie-launch` do the same. The dump is deleted from the server after 90 days. See [crash-reports.md](crash-reports.md).
