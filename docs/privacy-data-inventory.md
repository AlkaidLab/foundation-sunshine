# Privacy data inventory: what each client sends and what the server keeps

This list answers three questions: what is sent, why it is needed and how personal details are removed. Every entry names the code (`file:line`); the code locations are found by `scripts/telemetry/build_inventory.py` when the page is generated, so they follow the code.

## In one paragraph

Two independent switches (error reports, usage statistics), on by default; when one is off, nothing of that kind is sent. One exception: a feedback report the person sends on purpose, and its log, go out whatever the error-reports switch says (pressing Send is the consent for that one report). The data goes only to the developers' own server, `api.alkaidlab.com` (a Cloudflare Worker), not through an advertising network, and is not sold. Apart from feedback a person writes by hand, the anonymised program log that goes with a crash report or a feedback report, the log excerpt after a serious stream problem and the last lines of a component's own log that an error report carries (only while error reports are on, cleaned text, see Never sent) there is no free text anywhere: names, paths, addresses and accounts are not in the payload to begin with, and are removed from the logs before they leave the computer.

The server does not store IP addresses, only the country code Cloudflare supplies; Workers Logs are off `worker:wrangler.toml:12`. The connection itself necessarily crosses the network and Cloudflare, as the network provider, sees the connecting address at the transport layer; that layer is not ours, and our code does not read, store or log it.

## Never sent

- Screen content, audio, keystrokes, files, clipboard content. The one exception is a screenshot the person adds to a feedback report themselves (the capture of the control panel's own window, or a picture they choose or paste): they see it, can cover places in it or remove it, and it is sent only with that one report (see `user_report`). Nothing is captured or read from the clipboard by itself.
- The name of the computer, the Windows or macOS account, a device or a client; the name of a game or an application (a game is at most one of nine catalogue words).
- File paths, IP addresses, MAC addresses, ports, pairing identifiers, Steam, miHoYo or other account ids, Mirror酱 CDKs, passwords, tokens, cookies.
- A program log that has not been anonymised. The text a person typed (`user_report.message`) is sent only when they press Send, after the panel showed what leaves; the log the program wrote is a different kind of text, in two cases kept apart. **The log of a crash report** goes only when error reports are on. **The log of a feedback report the person sends** is attached by the host when it receives the report, and pressing Send is the consent for that one send, whatever the error-reports switch says. Both go only after the anonymisation described in the "program log" row above. If the log cannot be read or uploaded, the feedback is still sent, without the log. With both switches off, no install id is recovered or created for the report: it uses a one-time random id of its own (for the report and its log only), and the server counts it as no activity, session or install.
- Free text has exactly four places, and (3) and (4) and the crash-report half of (2) only while error reports are on (the first needs the person to press Send, and the feedback-report log of (2) goes with it, whatever the switch says; a contact the person leaves is a fifth text, typed on purpose to be answered and shown only in the issue of that report): (1) `user_report.message`, sent when the person presses Send, after the panel showed what leaves; (2) the program log attached to a crash report or a feedback report (`user_report.log_ref`): the crash-report log only while error reports are on, the feedback-report log with the report itself whatever the switch says, both anonymised on this computer with the rules of the "program log" row above (user and computer names, user segments of paths, IP and MAC addresses, e-mail, serial numbers, tokens, PINs, Wi-Fi names, game account names; a name that stands between quotes is not removed by those rules unless it is one of these things); (3) the log excerpt after a serious stream problem (`stream_anomaly`, `log true`): the last two minutes of the host's own log; (4) `error_report.log`: the last up to 40 lines (200 characters each) of a component's own log, with the first report of an error. For (3) and (4) text between quotes, brackets and braces is dropped as well (a short bracket that only holds a code, such as `[E12]`, stays) and names, folders, addresses (IPv4 and IPv6), e-mail addresses and keys are cleaned. All four stay text, not a fixed list of words, so what a line happens to say after the cleaning is sent. Everything else is a fixed word, a number or an id of our own.

## How it is enforced

- The anonymisation of the program log has one set of test vectors, a row of cases for every category (names, paths, addresses, serial numbers and device ids, tokens, PINs, Wi-Fi names, accounts, and what must stay): `tests/data/log_scrub_vectors.json` (C++, `tests/unit/test_log_scrub.cpp`), the report service's `test/log-scrub-vectors.json` (TypeScript reference) and the Python port of the private repository's decode workflow. The client anonymises first; the service only spot-checks the first and last 64 KiB and refuses the whole log on a hit; the workflow scrubs the whole log again before it shows a line and replaces the stored file.
- The sender has an allow-list: an event name or a property that is not listed is dropped before it leaves the computer `src/telemetry/events.cpp:474` (unit tests in `tests/unit/test_telemetry.cpp`).
- The Worker checks the same list again; a property of the wrong shape is dropped, never "cleaned and kept" `worker:src/schema.ts:61`.
- The three scrubbers run the same test vectors: `tests/data/telemetry_scrub_vectors.json` (C++), m3e `test/scrub-vectors.json` (JS), Worker `test/scrub-vectors.json` (TS); `scripts/telemetry/check-scrub-vectors.sh` checks the three copies are identical. The vectors plant a fictional account name, computer name, paths, IPs, MACs, UUIDs, e-mail and tokens.
- The byte-level redaction of crash dumps has one implementation each in C++, Rust and C#, with the same test vectors.
- Consent: error reports and usage statistics are independent; the host checks before every send, and events from the pages are checked once more by the host `src/telemetry/service.cpp:228`.
- The person can read "what is sent and what is not" under About › Privacy and open "See what will be sent" for the exact next send `src/telemetry/telemetry.cpp:470`.

## Merged records of high-volume usage and experience data

The host sender holds the high-volume records (start and exit, feature use, settings changes, stream start/end/quality, start-up times, page loads, page performance sketches and API latency) in memory and uploads them merged: at most once every six hours and when the program exits (`src/telemetry/service.cpp`, `src/telemetry/events.cpp:aggregate_events`). Records with the same name and the same non-numeric properties become one record that carries the number of occurrences in an extra `count` field; counters and bucket vectors of the page sketches are added up, other numbers are averaged. No field is added except `count`, and nothing that was not allowed before is sent. The Worker checks every merged record against the same allow-list as a single one, stores no raw row for it, and keeps its count in the daily usage figures. Records that are not merged and leave one by one as before: feedback reports, crash and error reports, install and update failures, stream health summaries and the record of a turned-off choice. A record that waits for the interval is also removed when its choice is turned off, and it appears in "See what will be sent" in its merged form. If the program is killed before it can exit normally, the records held for the current interval are lost.
