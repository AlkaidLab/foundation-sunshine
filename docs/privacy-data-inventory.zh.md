# 隐私数据清单：每个客户端发送什么、服务器保存什么

这份清单回答三个问题：发送了什么、为什么需要、怎样去除了个人信息。每一条都标出了代码位置（`文件:行号`）；代码位置由 `scripts/telemetry/build_inventory.py` 在生成时查找，所以会随代码更新。

## 一句话

两个独立的开关（错误报告、使用统计），默认开启，关闭后该类内容不再发送。有一个例外：用户主动发送的反馈及其日志，不受错误报告开关限制（点「发送」就是同意发送这一条）。数据只发往开发者自己的服务器 `api.alkaidlab.com`（Cloudflare Worker），不经过广告网络，不出售。除用户亲手写的反馈、随崩溃或反馈报告附带的匿名程序日志、严重串流问题之后的日志摘录和错误报告携带的组件日志最后几行（仅在错误报告开启时，清洗后的文本，见「从不发送」）外，没有任何自由文本；名称、路径、地址、账号在发送前就不在载荷里。

服务器自己不保存 IP 地址，只保存 Cloudflare 给出的国家代码；Workers 日志已关闭 `worker:wrangler.toml:12`。连接本身必然经过网络，Cloudflare 作为网络服务商在传输层看得到连接的 IP，这一层不由我们控制，我们的代码不读取、不保存、不记录它。

## 从不发送

- 屏幕内容、声音、键盘输入、文件、剪贴板内容。唯一的例外是用户自己加到反馈里的截图（控制面板自己窗口的截图，或者用户选择、粘贴的图片）：发送前用户能看到，可以遮住其中的位置或移除，只随这一条反馈发出（见 `user_report`）。不会自动截取屏幕，也不会自动读取剪贴板。
- 电脑名、Windows 或 macOS 账号名、设备名或客户端名；游戏名和应用名（游戏最多是九个目录词之一）。
- 文件路径、IP 地址、MAC 地址、端口、配对标识、Steam、米哈游或其他账号 id、Mirror酱 CDK、密码、令牌、Cookie。
- 未经匿名处理的程序日志。用户亲手写的报告文字 `user_report.message` 是人输入的自由文本，只在用户按下「发送」后发出，且表单事先展示过；程序自己写的日志是另一类文字，分两种情况：**崩溃报告的日志**只在错误报告开启时发送；**用户主动提交的反馈的日志**由主机在收到反馈时附加，点「发送」就是同意发送这一条，不受错误报告开关限制。两者都先经过匿名处理（见上面「程序日志」一行）。日志读取或上传失败时，反馈仍会发出，只是不带日志。两个开关都关着时，不会为这条反馈恢复或新建安装编号，它使用一次性的随机报告编号（只用于这条反馈和它的日志），服务器不把它算作活跃、会话或安装。
- 自由文本只有四处，（3）（4）以及（2）中随崩溃报告附带的日志仅在错误报告开启时发送（第一处需要用户按下「发送」，（2）中随反馈报告附带的日志随它发出，两者都不受开关限制；用户留下的联系方式是为了被回复而亲手填写的，只显示在这一条反馈的 issue 里）：（1）`user_report.message`：用户按下「发送」后发出，面板事先可以查看将发送的内容；（2）随崩溃报告或反馈报告附带的程序日志（`user_report.log_ref`）：前者仅在错误报告开启时发送，后者随反馈报告发出、不受开关限制，都在本机按上面「程序日志」一行的规则匿名处理（用户名和电脑名、路径里的用户名、IP 和 MAC 地址、邮箱、序列号、令牌、PIN、Wi-Fi 名、游戏账号名；引号里的名字除非属于这些类别，否则不会被这些规则去掉）；（3）严重串流问题之后的日志摘录（`stream_anomaly`，`log true`）：主机日志最近两分钟；（4）`error_report.log`：组件自己日志的最后至多 40 行（每行至多 200 个字符），随一个错误的第一条报告发送。（3）和（4）还会丢弃引号、方括号和花括号里的文字（只装代码的短方括号如 `[E12]` 保留），并清洗名称、文件夹、地址（IPv4 和 IPv6）、邮箱和密钥。四处都仍然是文本，不是固定词表，所以清洗后一行恰好写了什么就会被发送。其余都是固定词、数字或我们自己的 id。

## 怎样保证

- 发送端有白名单：未列出的事件名和属性在离开电脑前就被丢弃 `src/telemetry/events.cpp:474`（单元测试 `tests/unit/test_telemetry.cpp`）。
- Worker 对同一份名单再检查一次；格式不对的属性被丢弃，不会被「清洗后保存」`worker:src/schema.ts:61`。
- 三种语言的清洗规则用同一份测试向量：`tests/data/telemetry_scrub_vectors.json`（C++），m3e `test/scrub-vectors.json`（JS），Worker `test/scrub-vectors.json`（TS）；`scripts/telemetry/check-scrub-vectors.sh` 检查三份相同。向量里是虚构的用户名、电脑名、路径、IP、MAC、UUID、邮箱、令牌。
- 崩溃转储的字节级清洗在 C++、Rust、C# 各有一份实现和同样的测试向量。
- 程序日志的匿名处理有一份共用的测试向量：`tests/data/log_scrub_vectors.json`（C++，`tests/unit/test_log_scrub.cpp`）、Worker `test/log-scrub-vectors.json`（TS，参考实现）、私有仓库里解码工作流的 Python 版；向量里是虚构的用户名、电脑名、路径、IP、MAC、序列号、令牌、PIN、Wi-Fi 名、账号名，每一类都有。客户端先处理；服务端只抽查开头和结尾各 64 KiB，发现个人信息整份拒收；解码工作流在显示任何一行之前再整份清洗，并替换存储的文件。
- 同意：错误报告和使用统计各自独立；主机在每一次发送前都检查，网页发来的事件由主机再检查一次 `src/telemetry/service.cpp:228`。
- 用户可随时在「关于 › 隐私」看到「会发送什么」，并用「查看将发送的内容」看到下一次发送的原文 `src/telemetry/telemetry.cpp:470`。

## 高频使用与体验数据的合并上传

主机发送端把高频记录（启动与退出、功能使用、设置更改、串流开始/结束/质量、启动耗时、页面加载、页面性能分布和接口延迟）先放在内存里，合并后上传：最多每六小时一次，程序退出时也会发出（`src/telemetry/service.cpp`、`src/telemetry/events.cpp:aggregate_events`）。名称和非数值属性都相同的记录合成一条，多出一个 `count` 字段表示发生次数；页面分布里的计数和桶向量相加，其他数值取平均。除 `count` 外不增加任何字段，也不会发送以前不允许的内容。Worker 用与单条记录同一份白名单检查合并后的每一条，不为它保存原始行，只把次数计入每日使用数字。仍然逐条发送、不合并的有：问题反馈、崩溃与错误报告、安装与更新失败、串流健康摘要，以及关闭某项选择的记录。等待间隔的记录会在对应选择被关闭时一并清除，「查看将发送的内容」里看到的就是合并后的样子。如果程序在正常退出之前被强行结束，当前间隔内暂存的记录会丢失。
