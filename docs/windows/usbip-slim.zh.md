# USB/IP 签名包原样分发

本方案固定 usbip-win2 v.0.9.8.1 的 x64 安装器和 SHA-256，使用仅构建时运行的
Inno Unpacker 2.71.4（ui_2_2_14 发布包）提取。旧 innoextract 1.9 和其当前主线最多支持
Inno 6.3.3，不能读本包的 Inno 7.0.0.3。无需执行上游安装器，也不重新编译或签名驱动。

驱动包的全部六个文件（两个 INF、两个 SYS、两个 CAT）逐字节保留，清单见
`scripts/packaging/usbip-payload.json`。Windows 构建必须用 SDK SignTool 验证两个
catalog 的 `/kp` 策略及 `/kp /c` 下四个 INF/SYS 的成员关系；任何失败均停止打包。
这比仅检查 CAT 的 Authenticode 更完整。原始 INF 的广泛匹配保持不变，外层根集线器
guard 继续检查并清理异常状态，绝不通过修改 INF 缩小匹配。

## 上游安装行为对应

| 上游 setup.iss 步骤 | 对应实现 |
| --- | --- |
| main：usbip.exe、devnode.exe、所有 DLL | 原样复制四个工具文件至共享 USBip 目录 |
| client：package 全部文件 | 原样复制至 driver 子目录，SHA-256 固定 |
| VC++ 安装程序 | 有意不分发、不执行；从同一个固定安装器的运行库内容提取 app-local DLL |
| pnputil 安装 usbip2_filter.inf | 系统 pnputil `/add-driver … /install` |
| devnode install UDE INF 和 ROOT\\USBIP_WIN2\\UDE | 先由 pnputil 暂存 UDE INF，再用原版 devnode 注册根设备 |
| AddService、AddReg、AddFilter | 全部交给原样签名 INF，脚本不重写服务或驱动注册表 |
| RegisterDetachTask | Task Scheduler 2.0 注册同名 LocalService 任务，保留关机/重启事件触发及原始 detach 参数 |
| PrepareToInstall 卸载旧包 | 先只读判断归属；仅确认自有旧包后使用固定 AppId 原 uninstaller，外部安装原样保留 |
| devnode remove | 调原版 devnode remove，失败仍继续其他清理并返回失败 |
| DeleteOemDriver 双查找 | DISM Get-WindowsDriver 的结构化包信息匹配两个原始 INF，再由 pnputil 删除 |
| UnregisterDetachTask、移除文件和卸载项 | 删除任务、驱动包、自己的 receipt 和所列文件；保留不相关文件 |
| AlwaysRestart / UninstallNeedRestart | 旧版接管及系统返回 3010 时报告需重启，不自动重启 |
| GUI、SDK、PDB、桌面图标、测试证书 | 有意不分发、不创建、不导入 |

上游 tag 的 setup.iss 与安装器内重建的 [Run] 同时核对；本安装器实际包含 devnode
安装/卸载步骤，不能只从某一份源码推断。自有旧包卸载和新包安装均在 guard 的快照与验证
之间；外部安装在 guard、状态文件、互斥量和复制文件之前返回。失败的清理继续完成其余步骤，保留必要恢复文件；根集线器恢复不完整返回 103，
不能宣称回滚成功。互斥量防止两个顶层生命周期操作并发，内部回滚不重复取锁。

## 实机观察（测试虚拟机，Windows 11 26H2，2026-11-17）

这些事实只能用真实的上游安装器得到，夹具里的模拟值曾与之不符，已据此修复并补回归用例：

- 上游 Inno 安装器写入的 `InstallLocation` 带结尾反斜杠（`C:\Program Files\USBip\`），
  `UninstallString` 是 `"…\unins000.exe" /LOG`。归属判断改为规范化后不分大小写比较路径，
  卸载命令只接受带或不带可选 `/LOG` 的引号形式，实际执行的参数仍是固定的。
- `Get-PnpDevice -PresentOnly:$false` 并不返回全部设备，只返回不在位的设备；要包含不在位节点就不要传该开关。
  此前卸载因此跳过 `devnode remove`，留下硬件 ID 为 `ROOT\USBIP_WIN2\UDE` 的幽灵根节点。
- 旧版 FS 安装器静默运行上游安装器时使用其默认组件，实际装上了 GUI、SDK 和 PDB
  （`Selected Components: main,client,gui,sdk,pdb`）。这样的安装和用户自己用默认选项装出的上游卸载项
  逐值相同（连卸载命令里的 `/LOG` 都一样），所以只看卸载项无法判断是谁装的。可靠的区分依据见下面
  「旧版 FS 安装器装出的完整版」一节。
- 接管成功后，FS 目录里作为来源证明的上游安装器（约 26 MB）会被删除。

## 旧版 FS 安装器装出的完整版（2026-11-18）

旧版发行安装器静默运行上游安装器 `USBip-0.9.8.1-x64.exe`（参数 `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART
/RESTARTEXITCODE=3010 /SP-`，不带 `/LOG`），装出的是默认完整组件。用户自己用默认选项装出的状态，在上游
卸载项里逐值相同：`UninstallString` 都带 `/LOG`（上游编译时就开了日志，不是调用者传的）、
`Inno Setup: Selected Components`、`Selected Tasks` 都一样。「谁运行了上游安装器」只在 FS 一侧留下痕迹：

| 证据（全部同时满足才算 FS 装的） | 为什么能区分 | 缺失或矛盾时 |
| --- | --- | --- |
| 恰好一条固定 AppId 的上游卸载项，没有 FS 的瘦身 receipt | 两个注册表视图各有一条，或有 receipt，来源就说不清 | 外部管理 |
| FS 目录 `scripts\usbip` 里仍有固定哈希的 `USBip-0.9.8.1-x64.exe` | 只有选了 USB/IP 组件的 FS 安装才带它；但它不证明 FS 运行过，因为旧安装脚本发现同版本已装就直接退出，文件却照样被复制 | 外部管理 |
| 上游卸载项的组件恰好是 `main,client,gui,sdk,pdb`，没有被取消的组件 | 静默默认运行的结果；用户改过选项就矛盾 | 外部管理 |
| 安装目录里恰好一个 `unins*.exe`，且是登记的那个，位于标准安装目录 | 只运行过一次上游安装；重装或叠装会多出 `unins001.exe` | 外部管理 |
| FS 根集线器 guard 日志里有一次完整事务：`snapshot` 行的 `filter packages` 为空，随后是 `verify ok`，中间没有 ROLLBACK、REFUSED 或错误行；上游安装的所有文件（usbip.exe、devnode.exe、libusbip.dll、wusbip.exe、卸载程序）的创建时间和卸载数据 `unins*.dat` 的最后写入时间都落在这次事务内（两端各留 2 秒） | 旧安装脚本发现同版本已装就在 guard 之前退出，日志里没有这次事务；用户之后另装会产生不在窗口内的时间戳；过滤包列表为空说明安装前系统里没有任何 usbip-win2 | 外部管理 |
| 上游卸载项的 `InstallDate` 等于那次事务的日期 | 与上一条时间窗口互相印证 | 外部管理 |

时间戳依据：Inno Setup 安装的每个文件都是新建的，创建时间就是安装时刻，修改时间则保留源文件的。2026-11-17
在一台真实的、装过上游的机器上只读核对：同一次安装的所有文件创建时间相同（精确到秒），`unins001.dat`
在 1 秒内写完；该机器的 FS 目录里没有 guard 日志，上游安装时间（10-20）早于 FS 的首次安装（11-07），
这套证据正确地判定为「不是 FS 装的」。

边界：guard 在 2026-11-16 的发行版才加入，更早的旧版 FS 装出的完整版没有这条日志，一律按「用户自己装的」
处理，只能由用户在面板里点「清理旧版 USB/IP」。guard 日志由 FS 在 Program Files 下写入，普通用户不可写。

## 用户确认的替换（面板「清理旧版 USB/IP」）

当安装被判为外部管理，但满足「恰好一条固定 AppId 的上游卸载项、安装在标准目录、登记的卸载程序在该目录内」
时，`usbip-package.ps1 -Action status` 返回 `replaceable: true`，面板据此显示按钮。版本不限：由用户决定，
替换装的是固定的 0.9.8.1。

- 按钮先说明会做什么，用户确认后面板以管理员权限执行 `usbip-package.ps1 -Action replace`。
- `replace` 是唯一允许处理未证明归属的安装的入口：先带确认判断一次，取得生命周期锁后再带确认判断一次，
  任何一次不满足就以 107 退出，不改动任何东西。
- 满足后走和自动接管相同的受保护路径：先校验精简载荷，再做根集线器 preflight 和 snapshot，再用固定
  参数运行已登记的上游卸载程序，再装精简包，最后 guard 验证；失败时清理半装的精简包，guard 清理并验证。
- 回滚的含义：载荷校验失败、guard 拒绝等发生在上游卸载之前的失败，系统保持原样（旧版仍在）。上游已卸载后
  精简包安装失败，则清除半装状态并恢复根集线器，系统处于「未安装」而不是「半装」；FS 不再携带 26 MB
  的上游安装器，不能原样装回旧版。面板在失败后重新读取实际状态并如实显示。
- 面板在有已挂载的 USB 设备或正在串流时拒绝执行。

## 载荷随主机安装（issue #1461）

安装脚本（`usbip-package*.ps1`）一直随主机安装，而 `scripts\usbip` 载荷（约 3.4 MB）和许可证原先只在安装程序里
勾选了「USB/IP」组件时才落盘；该组件默认不勾选。面板的「一键修复 USB/IP」从这份载荷安装，没勾选组件的主机上
它在校验载荷时失败：`cannot verify the shared transport: 系统找不到指定的路径。 (os error 3)`，面板把这个错误码
说成「版本不一致」，让人去清理一个本来就不存在的传输。

现在载荷和许可证属于 `assets` 组件，每次安装都落盘；组件只决定安装程序是否当场运行 `install-usbip.bat`。
只有文件、没有安装：没有驱动、没有登记、没有 root hub 筛选驱动，面板仍要用户确认后才安装。已装的旧版本在下次
更新安装时补上载荷；在此之前面板会说明缺的是哪一部分（`USBIP-SETUP-019`）并给出重新运行安装程序的步骤，
且在清理共享传输之前就停下。

无登记的残留：另一个工具自带的 usbip-win2 被它自己的卸载程序移除后，驱动服务、工具或控制器可能还在，但
「已安装的应用」里没有任何项。主机把它判为外部管理且不兼容（`reason=no-registration`，安装退出码 106），面板给出
`pnputil /delete-driver`、`sc.exe delete` 和设备管理器的手动清理步骤；不自动删除，因为无法区分它是被遗弃的残留，
还是用户有意保留的另一个工具的驱动。

## 运行库与许可证

`objdump -p` 检查两个 EXE、libusbip.dll、resources.dll 及运行库自身的导入表：
完整非系统依赖闭包为 MSVCP140.dll、MSVCP140_ATOMIC_WAIT.dll、VCRUNTIME140.dll、
VCRUNTIME140_1.dll。其余依赖为系统 DLL 与 Windows 10 内置 UCRT API 集。
固定运行库为 14.51.36247；不是任意构建机上较旧的 VC 安装。构建提取固定 Burn CAB
字节区间，交给 Windows 自带 expand 解包，再逐文件核对固定哈希与微软签名。
不执行运行库安装程序，不分发 MSI、CAB 或安装 EXE。上游原有动态链接保持不变。

微软文档允许 app-local，但因维护成本推荐集中安装。本方案按包体积要求选择允许的
app-local 方式，并负责运行库版本维护；不采用已弃用的 merge modules，也不改成静态链接。
再分发以拥有有效 Visual Studio 使用许可并遵守其软件许可条款为前提，本文不宣称替代
该许可。来源记录 usbip-slim-ms-vc-redist-20261117 与 usbip-slim-ms-redist2026-20261117（2022 清单亦作交叉核对）。
usbip-slim-license-20261117 记录的 usbip-win2 BSD-2-Clause 原文统一放入 `third_party/licenses/usbip-win2/LICENSE`，
在 payload 中保留副本；与第三方声明任务采用相同目录。

## 探测、性能与验证边界

共享工具位置继续使用原标准目录，主机 doctor 已从工具文件及 UDE/VHCI 服务探测，
不依赖上游卸载项，因此两种安装均兼容。新的安装记录附加 InstallLayout、SourceSHA256、
InstallLocation 和版本；Panel 需同时识别这份 receipt 和旧包，执行时验证工具/驱动字节。
`status` 不把注册表版本当作驱动可用的证据：还检查工具完整性、唯一根设备问题码及
注册驱动哈希。

目标是解压后的核心 payload 小于 4 MiB；原安装器 26,083,632 字节，提取 payload
3,476,484 字节（含清单和许可证）。这不是最终整包大小；最终安装器和便携包须比较同一
构建配置的产物。更换打包与安装机制不改传输热路径，没有增加每帧复制、分配、系统调用
或锁；吞吐、延迟、CPU 和跨实现性能没有测量，不据此声称性能领先。

Windows 使用 PowerShell 5.1、系统 PnPUtil/DISM、原版 devnode 与 Task Scheduler，避免
额外目标机运行时；构建工具用 Python 标准库。原签名驱动要求 Windows 10 1903，不能
通过修改 INF 改变最低版本。Linux 仅作提取/隔离回归；macOS、Android、iOS、HarmonyOS
不受此 Windows 分发变更影响，没有新增 Backend 或 Adapter。USB/IP 生态兼容性没有
本卡实测，远程 USB 与原生手柄需独立验收。真实设备、资源授权、跨租户隔离均未核实。

Windows CI 验证文件和签名，不在共享 runner 安装驱动。虚拟机全新安装、旧包接管、卸载、
模拟 guard 失败回滚和真实远程 USB/原生手柄测试通过之前，PR 保持草稿，不得合并。

## 安装归属与兼容规则（2026-11-17）

| 观察结果（从上往下优先） | 归属 | 安装动作 | 卸载动作 |
| --- | --- | --- | --- |
| 检查失败、注册冲突或来源不明 | 外部管理 | 不改动，提示检查或自行选择替换 | 不改动 |
| 有 GUI 或 SDK（wusbip.exe、include 或 lib），且「旧版 FS 安装器装出的完整版」一节的全部证据没有同时满足 | 外部管理 | 同版本可复用；不改动 | 不改动 |
| 版本不同或无法读取 | 外部管理 | 不改动，返回 106，提示用户自行决定 | 不改动 |
| 同版本、自有固定 receipt、来源哈希与位置匹配，且没有旧 ARP 项 | 自有瘦身版 | 校验后复用，必要时只修复自有包 | 受 guard 保护卸载自有包 |
| 同版本、无 GUI/SDK、无瘦身 receipt，主机 scripts/usbip 中仍有固定版本原安装器 | 自有旧版 | 固定 AppId 卸载器接管 | 仅处理已确认自有旧版 |
| 同版本、带 GUI/SDK，且「旧版 FS 安装器装出的完整版」六条证据同时满足 | 自有旧版 | 固定 AppId 卸载器接管 | 仅处理已确认自有旧版 |
| 没有注册、工具、驱动服务或残留 | 未安装 | 安装瘦身版 | 无操作 |

旧版兼容判断是明确的历史例外；原安装器还必须匹配固定 SHA-256，文件名存在本身
不足以证明来源。普通安装 journal 的成功记录不单独作为所有权证据，因为复用外部
安装也会记录成功。没有可靠记录而又不满足上述完整例外时，一律按外部管理处理。
来源：usbip-policy-reg-20261117（ARP 值不证明安装者）、usbip-policy-read-20261117
（LiteralPath 只读检查）、usbip-policy-files-20261117（固定目录内文件检查）。

兼容范围严格为 0.9.8.1，不接受 0.9.8.0、0.9.8.2 或推断的“更新版本兼容”。这是
已固定且现有主机和面板共同使用的工具/驱动组合，而非跨版本 ABI 承诺。版本元数据
只决定能否候选复用；外部 status 继续核对 CLI、库、注册 UDE/filter 驱动的固定字节，
并检查唯一根设备的硬件 ID 和问题码。Panel 保留现有 CLI/注册驱动验证与 port 只读
探测。驱动文件版本 12.1.30.403 与发行版本 0.9.8.1 是两种不同版本号，不能相互代替。
GUI/SDK 与重复上游卸载器不会阻止兼容工具的复用，也不授权删除它们。

安装器的独立根设备 helper 同样先判定归属，外部安装的 install、repair、uninstall
不会登记、改名、禁用或移除任何节点。主机体检显示“外部管理”，面板保留就绪功能，
并隐藏托管安装和清理按钮。主机和面板都不会自动卸载外部包；满足条件时面板显示用户
自己点的「清理旧版 USB/IP」，确认后才替换（见「用户确认的替换」一节）。

夹具覆盖完整外部版、自有同版本旧包、旧版 FS 安装器装出的完整版及其每一条证据缺失或矛盾的变体、不兼容版、瘦身版、未安装，以及包含两个
卸载器、GUI/SDK、运行中的双驱动服务和现有根节点的观察布局。CI 只用模拟注册表
和隔离文件；不安装真实驱动。不改 INF，不重新签名，不修改已有驱动字节。
只有可快照的测试系统具备后才验证全新安装、接管、真实卸载与回滚；当前共享系统
仅允许对外部安装执行无修改路径并比较前后驱动、服务、注册表和文件。远程 USB、
原生手柄和麦克风的真实设备功能仍需各自独立实测，不能用只读 port 成功替代。

此改动是安装/探测控制路径，不触及 USB/IP 数据热路径。新增元数据查询和固定哈希
读取的延迟、分配、系统调用数及相对直接调用开销未测量。当前上游完整安装仍作为
原样复用对象；没有移植其他实现，也没有吞吐竞争结论。Windows 延用 PowerShell 5.1
和原生注册表/文件查询以兼容既有最低系统要求；C++ 体检仅只读查询。其他 OS 无新增
Backend，未构建、未运行；USB/IP 跨实现兼容和潜在 Adapter 未验证。

## 测试虚拟机实测（2026-11-18）

测试系统：Windows 11 Enterprise 评估版 26H2，每个场景前恢复到干净镜像；被测安装器是 `fix/usbip-legacy-cleanup`
（头提交 `0f675b595`）在 fork 上的 CI 产物，Panel 一侧用 foundation-panel #26（头提交 `c46af8b2a`）的 CI 产物。
「旧版发行安装器」是 v2026.1117 的安装器。每个场景记录安装前后的驱动包、服务、设备节点、USB/IP 目录、卸载项、
断开任务并逐类比较；没有接物理 USB 设备，也没有串流，所以真实远程 USB、原生手柄和麦克风不在覆盖范围内。

| # | 场景 | 结果 |
| --- | --- | --- |
| 1 | 旧版发行安装器装 USB/IP（默认组件），取证 | 通过。上游文件的创建时间都落在 guard 日志 `snapshot`（`filter packages` 为空）与 `verify ok` 两行之间，`unins000.dat` 的最后写入时间同样在窗口内，`InstallDate` 与事务同日；六条证据全部满足，判为自有旧版。重启后再判结果相同 |
| 2 | 在 1 的基础上装本安装器 | 通过。上游卸载，精简包装入并就绪，没有 GUI、SDK、PDB，没有上游卸载项，随包的上游安装器被移除；面板后端报告就绪且不是外部管理 |
| 3 | 用户自己装完整上游（默认组件），再装本安装器 | 通过。10 类 USB/IP 状态前后逐项一致；`status` 报告外部管理、`replaceable: true`；面板后端报告外部管理且可替换 |
| 4 | 在 3 的基础上执行 `replace` | 通过。退出码 3010；精简包就绪，上游卸载项、GUI、SDK 消失；之后卸载 USB/IP 并重启，状态与干净镜像逐项一致 |
| 5 | 载荷被改一个字节后执行 `replace` | 通过。载荷校验失败（退出码 1），发生在动上游之前，状态与之前逐项一致 |
| 6 | `replace` 时用 `-SimulateHubProblem` 制造根集线器故障 | 通过。guard 回滚，退出码 102，根集线器恢复，没有半装；重启后与干净镜像一致。回滚后上游已被卸载，系统处于「未安装」 |
| 7 | 在旧版发行安装器的安装上再出现 `unins001` | 通过。`unins001` 用复制 `unins000.*` 的方式制造（上游同版本叠装会重写 `unins000`，不会产生 `unins001`）；判为外部管理、`replaceable: true`，装本安装器前后逐项一致。另外实测：同版本叠装一次后，时间戳落在 guard 窗口之外，同样不自动处理 |
| 8 | 版本不兼容的上游（0.9.8.0，官方发行） | 通过。装本安装器前后逐项一致，`status` 报告 `compatible: false`、`replaceable: true`、版本 0.9.8.0；`replace` 后为固定的 0.9.8.1 精简版并就绪 |
| 9 | #1315 补丁后未重测的行为 | 通过。卸载记录两个注册表视图各一条时不自动处理，`replace` 也以 107 退出且无改动；登记的卸载程序在安装目录之外时不运行它（探针程序未被调用），`replace` 107 且无改动；取得锁之后重新判断：一个 `replace` 通过第一次判断后等待，另一个 `replace` 先完成，前者取得锁后重新判断，以 107 退出且没有改动（等待点用一行注入的延迟实现，其余脚本字节相同）；关闭驱动依赖下载时清除缓存里的可用标记，在最小 CMake 工程里验证（旧版保留标记，新版清除） |

观察到但不属于本改动的行为：
- 回滚（场景 6）之后、重启之前，驱动服务注册项仍在，此时 `status` 报告 `external`、`unsupported-version`，重启后恢复为未安装。
- 旧版发行安装器（11-16 之后）装出的状态，上游文件时间落在 guard 窗口内，识别证据在真机上成立；`usbip-win2-root.ps1 -Action install` 仍在测试机上返回 1（ALKAIDUSB 迁移的 Win32 203），与旧版行为相同，另有修复分支处理。
