# 桌面壁纸海报预览缓存修复设计

关联：#1471（问题报告）、#1021（完整缓存重设计，OPEN）、#1246（功能引入）、#1357（命中优化）。

本文是落地在现有实现（`src/nvhttp/poster.cpp`）上的修复设计，不推翻 #1021。#1021 的完整方案（WebP、WIC、元数据、LRU）继续作为独立演进。文中的行号对应 master `7aca9346a`，引用的文件在 `aa6699ab5` 之后的提交里没有改动。

## 1. 背景

#1246 在 2026-11-14 新增 `src/nvhttp/poster.cpp`。`image-path` 为 `desktop` 时，它把系统壁纸按比例生成全尺寸 PNG 与预览图并缓存为文件，#1357 再加入「变体已存在就跳过」。#1471 报告了四类问题，引入点排查（见 #1471 的分析）确认全部来自 #1246 的初始实现，此后的 #1254、#1279、#1357 均未触碰这些行为。

1. 缓存与临时文件写在壁纸源文件所在目录（如 Downloads），污染用户目录。
2. `write_atomically` 的临时文件在「写完、改名之前」进程被终止，或改名失败后连删除也失败时残留，且没有任何启动清理。
3. 缓存名包含 `filename().string()`。这段窄字符串是 UTF-8 字节，「鸿蒙壁纸1」的 `E9 B8 BF E8 92 99 …` 在创建文件时被按系统代码页（GBK）两两解码成「楦胯挋澹佺焊1」，落盘文件名乱码，缓存命中判断也随之失准。
4. 正式缓存因此永远落不了盘，#1357 的跳过永远不命中，4K 壁纸每次请求都重新解码、缩放、编码。

设计审查中发现第五个问题，它不在 #1471 里，独立于上面四条。

5. 预览没生成时服务端把原图发给客户端，而且发生在每一次换壁纸之后。`/applist` 触发生成，封面请求紧随其后，此时预览还在生成，客户端拿到的是原图。带 `v` 的响应被标记为 `immutable`，客户端会在整个壁纸版本期间一直保存这张原图。标准 Moonlight 请求的 `full` 变体本来就回原图。壁纸是几十 MB 的 PNG 时，封面等于下载原图，磁盘上的 200 KiB 预览没有被用到。

## 2. 根因小结

| 现象 | 根因 |
|---|---|
| 缓存与临时文件污染源目录 | `full_cache_path` / `preview_cache_path` 用 `source.path.parent_path()` 作缓存目录（`poster.cpp:174`） |
| `.tmp-*` 残留 | 进程在写入与改名之间退出。改名失败后删除也可能失败。没有启动清理 |
| 文件名乱码 | 创建走 `ofstream(const std::string &)`，窄字节按系统代码页解释。改名与删除走 `std::filesystem::path`，同一段字节按 UTF-8 还原成正确名字。文件落盘的那一刻起，代码就再也找不到自己刚写的文件，rename 必失败、remove 找不到文件 |
| 重复解码 | 上一条导致正式缓存不落盘，#1357 的存在性检查永远未命中 |
| 客户端拿到原图 | `preview()` 未命中时处理器直接回 `full`（`apps.cpp:236`），对原图大小没有上限，也不等后台生成。带 `v` 时响应是 `immutable`（`apps.cpp:250`） |

## 3. 目标

1. 预览与全尺寸缓存、临时文件只写入 `platf::appdata()` 下的缓存目录。
2. 非 ASCII 源路径的缓存命中判断与命中结果准确。
3. 进程启动后清理缓存目录里遗留的 `.tmp-*`，缓存目录有文件数上限。
4. 客户端可见行为不变，仍是 PNG/JPEG 变体与既有 Content-Type，尺寸策略不变。
5. 带 `fsVariant=preview` 的请求和桌面壁纸的封面请求只返回预览图。超过 200 KiB 的原图永不发给客户端，回退结果也不让客户端长期保存。
6. 请求线程不新增磁盘扫描、哈希或目录创建。唯一新增的阻塞是预览未生成时的有界等待，上限 2 秒，只发生在封面请求上。
7. 缓存路径上的任何异常与失败只影响缓存本身，不得影响主程序、请求处理与工作线程。

## 4. 非目标

- 不实施 #1021 的完整重设计（WebP、WIC 解码、metadata.json、LRU、壁纸变更通知），它继续作为独立演进。
- 不改变 `poster.h` 的 `preview_limit_bytes`（200 KiB）、`preview_longest_side`（640）与 12 次递减缩放。
- 除桌面壁纸外，其他应用的 `full` 请求（标准 Moonlight 不带 `fsVariant` 的请求）行为不变。把所有应用的封面都降到预览尺寸会改变用户上传的高分辨率封面的清晰度，不在本次范围。
- 不改变工作队列、`attempted` 去重与日志结构。
- 不自动回收源目录里的历史残留文件，原因见第 14 节。

## 5. 现有的检测时机与触发方式

当前实现没有定时器，也没有轮询线程。所有检测都由客户端的 HTTP 请求触发，本设计不改变这个模型。

| 触发 | 请求线程 | 工作线程 |
|---|---|---|
| `GET /serverinfo`（`nvhttp.cpp:591`） | 算列表标签 `appListEtag`，结果缓存 2 秒（`process.cpp:555`）。桌面应用的壁纸被故意排除在标签之外（`process.cpp:878`） | 无 |
| `GET /applist`（`apps.cpp:170`） | 对每个有封面的应用调用 `schedule()`，并在 `FsArtVersion` 里带上壁纸文件的大小和修改时间（`apps.cpp:163`） | 出队后执行 `build_variants` |
| `GET /appasset?type=poster`（`apps.cpp:229`） | `schedule()`，然后 `full()`，预览请求再加 `preview()` | 同上 |

- **壁纸路径**。桌面应用的 `image-path` 是 `desktop`，`app_art_asset_path()` 在每次 `/applist` 和封面请求里重新调用 `SystemParametersInfoW(SPI_GETDESKWALLPAPER)`（`process.cpp:927`）。换壁纸不需要重启 Sunshine，下一次 `/applist` 或封面请求就拿到新路径。
- **常驻客户端不会因为换壁纸重新拉列表**。客户端每隔几秒请求 `/serverinfo`，发现 `appListEtag` 变了才重新拉 `/applist`。壁纸不在标签里，所以换壁纸只有在客户端重新打开应用页、串流结束或手动刷新时才被看到。
- **第一个封面请求总是在预览生成途中到达**。客户端拉到新列表后立刻用新的 `v` 请求封面，而 `schedule()` 是在同一个 `/applist` 里才触发的，4K 图的解码加编码需要几秒。
- **客户端按版本长期保存封面**。`app_art_version` 的约定写在 `process.cpp:863`，带 `v` 的响应返回 `Cache-Control: public, immutable`（`apps.cpp:250`），版本不变时客户端不再请求。
- **版本识别**。key 由「路径 + 大小 + 修改时间」组成（`poster.cpp:167`）。壁纸换了（路径变）或被覆盖（大小、时间变）都会得到新 key，旧缓存自然不命中。
- **请求线程每次请求的固定成本**。读源文件的 `file_size` 与 `last_write_time`，算一次 key，最多三次 `is_regular_file`，对选中的文件读一次 `file_size`。ETag 首次需要整读选中的文件，之后走进程内缓存。
- **工作线程的成本上限**。`build_variants` 先探测预览是否已存在（`poster.cpp:298`），存在就直接返回，不解码。不存在时把 key 记入 `attempted`（`poster.cpp:302`），同一版本每个进程只解码一次，失败也不重试，直到进程重启或源文件变化。
- **排队去重**。`schedule()` 用进程内的 `queued` 集合去重（`poster.cpp:393`），工作线程取走任务后移除，排队期间的重复请求不会累积任务。

## 6. 缓存位置与命名

根目录是 `platf::appdata() / "covers" / "cache" / "poster"`。`platf::appdata()` 已在三个平台实现（Windows 为 exe 目录下的 `config`），目录创建在后台线程进行。

| 文件 | 命名 |
|---|---|
| 全尺寸 | `<key>-full.png` |
| 预览（含 alpha） | `<key>-preview.png` |
| 预览（不透明） | `<key>-preview.jpg` |

`<key>` 沿用现在的 `std::hash<std::string>`，只改一处输入。路径串从 `.string()` 换成 `file_handler::path_to_utf8(normalized_absolute_path)`，再拼上大小与修改时间。

- `path_to_utf8` 无损，不同路径不会得到同一个 key。`.string()` 在系统代码页下会把无法表示的字符替换掉。
- 文件名不再包含原文件名，全是 ASCII，乱码的源头消失。
- 保留 `std::hash` 的原因。key 在 `source_info()` 里计算，而 `representation()` 在请求线程上调用它（`poster.cpp:354`）。换成 SHA-256 等于在每个封面请求的请求线程上多做一次哈希，违反目标 6。几十个键用 64 位哈希不存在需要处理的碰撞，跨版本不稳定只会让旧缓存变成孤儿，第 8 节的上限会回收它们。
- 升级后已有的旧缓存全部失效一次，每个封面在后台重建一次。旧文件留在原处，不处理。

## 7. 临时文件与原子替换

`write_atomically` 保持「临时文件 + 同目录 rename」的原子替换模型，改两处。

1. 临时名在 `std::filesystem::path` 域内构造，在缓存路径上追加 `.tmp-<pid>`，全程不经过 `.string()`。
2. `ofstream` 使用 `std::filesystem::path` 重载，创建、改名、删除对同一个名字的解释一致。

写失败与改名失败的清理保持现状。

缓存名全 ASCII 之后，这一节看起来多余，但它必须保留。Windows 上缓存根在 exe 目录下，安装目录含中文时缓存路径本身就不是 ASCII，`poster.cpp:258` 的 `.string()` 加窄字符串 `ofstream` 会把同样的乱码不对称带回来。

## 8. 启动清理与容量上限

启动扫描只做一次，在 `run_worker()` 进入循环之前执行，不经过请求线程，不占队列。此后每次成功生成预览，工作线程在收尾时再跑一次同一扫描，长驻进程的缓存不会超过上限。

1. 删除缓存目录里全部 `*.tmp-*`。poster 每个进程只有一个工作线程，临时文件只存活毫秒级。
2. 剩余缓存文件超过 64 个时，按最后写入时间从旧到新删除，保留 64 个。

清理逻辑做成 `poster.h` 里一个以目录为参数的 `noexcept` 函数，返回「目录是否可用、删除的临时文件数、淘汰的缓存文件数」。`run_worker()` 用真实缓存根调用它，单测直接传临时目录调用，不依赖工作线程的启动顺序。

目录存在但拒绝写入的情况（只读的配置目录）用一个探测文件发现，同样算「不可用」。探测文件带临时文件名，异常退出留下的会被下一次清理带走。

上限的理由。每个壁纸版本写 1 到 2 个文件，预览固定写一个，全尺寸 PNG 只在比源文件小时才写（`poster.cpp:309`、`poster.cpp:321`）。手动换壁纸的用户碰不到上限。Windows 11 的「Windows 聚焦」每天自动换一张桌面壁纸，不设上限缓存会一直增长，64 个约为一到两个月的量。

## 9. 命中判断与 #1357

「变体已存在就跳过」的 `is_regular_file` 指向新的缓存路径。正式缓存落盘成功后跳过立即生效，4K 壁纸不再重复解码。

缓存落盘只解决重复解码。换壁纸后的第一个封面请求仍然是未命中，它拿到什么由第 10 节决定。

## 10. 封面请求的返回规则

适用两类请求。

- 所有应用带 `fsVariant=preview` 的请求。
- 桌面壁纸的全部封面请求，包括标准 Moonlight 不带 `fsVariant` 的请求。处理器用 `find_app()` 返回的 `ctx_t::image_path` 是否等于 `desktop` 来判断（`apps.cpp:202`）。

| 情况 | 返回 | Cache-Control |
|---|---|---|
| 源文件不超过 200 KiB，本来就不生成预览 | 源文件 | 带 `v` 时 `public, immutable`，现状不变 |
| 预览已存在 | 预览 | 带 `v` 时 `public, immutable` |
| 预览未生成，2 秒内出现 | 预览 | 带 `v` 时 `public, immutable` |
| 预览未生成，超时或工作线程已放弃这个版本 | 默认封面 `box.png` | `no-store` |

原图不作为任何情况的回退。

- **等待放在 `poster.cpp` 的一个新函数里**，即 `preview_when_ready(source, limit)`，`preview()` 保持不阻塞。三种情况立即返回，缓存目录不可用，这个版本既不在队列里也不在工作线程手上，预览已经出现。等待复用 `drained` 条件变量，工作线程每完成一个任务都会通知（`poster.cpp:348`）。
- **线程占用**。HTTPS 线程池是 4 个线程（`nvhttp.cpp:1352`），等待最多占住其中一个 2 秒，只在封面请求上发生，串流中没有封面请求。每个封面版本最多等一次，之后预览在磁盘上直接命中。极端情况下 4 个以上的封面同时等不到预览，`/launch` 最多推迟 2 秒。
- **升级后的第一次加载**。旧缓存全部失效，所有超过 200 KiB 的封面都要现生成一次。工作线程串行处理，普通封面的生成在零点几秒内完成。生成慢于 2 秒的那几张这次回默认封面。`no-store` 只保证回退响应不被缓存，本身不强制客户端重新请求；走 HTTP 缓存的客户端下次需要显示封面时会重新请求，重新请求时预览已生成就拿到预览。已核对的两个客户端见下一段，它们会把默认封面存下来，不再重新请求。
- **回退为什么不能标记 immutable**。客户端拉到新列表后立刻请求封面，此时预览还在生成。回退响应如果标记 immutable，客户端在整个版本期间都不会再请求预览。`no-store` 只让缓存方不保存这个响应，客户端下次打开应用页再次需要封面时会重新请求，此时预览通常已经生成。

已核对本机两个客户端的代码。Moonlight v+ 和 qt fork 都没有 HTTP 缓存层（vplus 的 OkHttp 未配置 cache，qt 的 `QNetworkAccessManager` 没有 `QNetworkDiskCache`），也不读 `X-FS-Poster-*` 这几个头，封面由它们自己的磁盘缓存按「主机 + appId」保存，只在文件缺失时重新请求。所以 `no-store` 对现有客户端无效，是为将来走 HTTP 缓存的消费方准备的；而「默认封面被长期持有」的根治办法在客户端，应用列表 JSON 里的 `FsArtVersion` 已经随壁纸变化，客户端比对版本失效封面缓存即可。在没有这个失效机制之前，这两个客户端会把收到的默认封面一直显示下去，直到本地封面文件被删除（vplus 在移除主机、手动清缓存、系统回收或缓存超过 20 MB 时删除，qt fork 没有自动失效）。
- **解码失败**。能进入 poster 的文件只可能是 png、jpg、jpeg（`process.cpp:808`），解码失败基本等于文件损坏。这类封面回默认封面，现有实现在这种情况下回原图，客户端同样显示不出来。
- **响应头**。`X-FS-Poster-Full-ETag` 和 `X-FS-Poster-Full-Length` 保持不变，桌面壁纸仍然计算一次 `full()`，只用它的 ETag 和长度填这两个头，内容不发出去。`X-FS-Poster-Variant` 描述响应体本身：预览（含不超过 200 KiB 的源文件本身）是 `preview`，回退的默认封面是 `default`。现有客户端都不读这些头，真实标记是为以后读头的客户端准备的。

## 11. 降级

- **缓存目录不可用**（`create_directories` 失败，例如配置目录只读）。清理函数返回「不可用」，工作线程记一条 warn 并置进程级标志，之后的 `build_variants` 在开头直接返回，不解码、不编码、不写盘，也不回退为写源文件目录。预览永远不会出现，等待函数看到标志直接返回，超过 200 KiB 的封面回默认封面，不超过 200 KiB 的照常返回源文件。
- **缓存缺失时客户端拿到什么**。`preview()` 对超过 200 KiB 的源返回空（`poster.cpp:366`），处理器按第 10 节的规则决定回什么。

## 12. 性能与异常约束

性能：

- 请求线程的计算量与系统调用次数不超过现状。key 仍是 `std::hash`，只换了路径串的来源，目录创建、清理、淘汰全部在后台线程。
- 有界等待是本次唯一新增的请求线程阻塞，上限 2 秒，等待期间不占 CPU。触发条件见第 10 节。
- 清理成本有界。启动时一次，之后只在成功生成预览后由低优先级工作线程再跑，扫描对象是缓存目录里最多几十个文件。
- 命中路径不新增读取，与现有实现一致。
- 预览生成仍在单工作线程并以低优先级运行（`lower_worker_priority` 保持），不占用编码与串流资源。

异常：

- 现有的会抛出的文件操作重载全部改成 `error_code` 重载，共五处。`representation()` 的三个 `is_regular_file`（`poster.cpp:357`、`362`、`364`），`schedule()` 锁外的 `absolute().lexically_normal()`（`poster.cpp:390`），`run_worker()` 持锁期间的同一表达式（`poster.cpp:340`）。前四处都在 `build_variants` 之外，最容易漏。
- `run_worker()` 里每轮任务和启动清理各自包在 `try` / `catch (...)` 里。现在 `build_variants` 没有任何兜底（`poster.cpp:343`），线程是 detached 的，异常逃逸会直接 `std::terminate`。任何异常只丢弃当前任务并记一条 warn，队列、线程与主程序继续运行。
- `schedule()` 不向调用方抛出。文件操作走 `error_code` 重载，启动工作线程失败时记一条 warn 并在本进程内停止缓存生成。
- 等待函数不向调用方抛出。条件变量的 `wait_for` 可能抛出 `std::system_error`，包在 `try` / `catch` 里，失败按未命中处理。
- 缓存相关的一切失败都收敛为「没有缓存」，不存在会让主程序、请求处理或工作线程退出的路径。

## 13. 并发与多实例

- 临时名含 pid，两个实例同时写同一张壁纸时互不覆盖。rename 在同一目录内原子，后完成者生效。
- 一个实例的启动清理可能删掉另一个实例正在写的临时文件。被删的一方本次构建失败并按 `attempted` 不再重试，该进程内这张壁纸走第 10 节的回退。这个窗口只有毫秒级，不为它加保护。
- 工作线程开始处理一个任务时记下正在处理的版本，等待方据此判断它是否已经放弃。等待方只在工作线程通知后重新检查文件，不持锁做文件操作。
- `attempted` 去重保持每进程语义。

## 14. 放弃的方案

| 方案 | 放弃原因 |
|---|---|
| SHA-256 作 key | 见第 6 节。请求线程多一次哈希，与目标 6 冲突，`std::hash` 没有需要处理的碰撞 |
| 临时文件的 60 秒保护窗口 | 只有一个工作线程，写临时文件是毫秒级。为多实例并发写同一张壁纸加时间窗口属于假设场景 |
| 清理「置标志 + 提交到工作队列」 | 单工作线程，启动扫描放在 `run_worker()` 开头，生成后的维护在同一线程直接调用，都不需要新的任务类型，`schedule()` 一行不改 |
| 源目录历史残留回收 | #1471 截图里的残留是 `.tmp-*`，旧临时名带 `std::hash<std::thread::id>`（`poster.cpp:258`），线程已不存在，名字无法复现。按旧公式只能构造出三个正式缓存路径，而非 ASCII 源的这三个文件因为 rename 必败从未落盘。这个方案清不掉 #1471 报的文件，只能顺带删掉 ASCII 名的旧封面缓存，收益小于风险，残留由用户手动删除 |
| 未命中时先回原图 | 原图可能几十 MB，并且被客户端按版本长期保存，预览生成后也不会再被请求 |
| 小于某个阈值的原图照常回 | 规则里多一个需要校准的数，而等待对普通封面只有零点几秒 |
| 换壁纸时在后台提前生成（轮询或变更通知） | 客户端拉到新列表后几毫秒内就请求封面，提前生成同样来不及。定时线程在进程退出时可能在运行库已经拆除后醒来。Windows 聚焦每天换图，会解码没人看的壁纸 |
| 请求线程同步快速解码（WIC 缩放解码） | 请求线程要初始化 COM，新增一套平台相关的解码路径，等于把 #1021 的一部分提前 |
| 无上限等待 | 占住 4 个 HTTPS 线程中的一个，8K PNG 要等好几秒 |
| 其他应用的 `full` 请求也只回预览 | 会把用户上传的高分辨率封面降到 640 像素，标准 Moonlight 在高分屏上会变模糊。本次只对桌面壁纸和显式的预览请求生效 |

## 16. 测试

单测前置条件。`poster_unit_tests` 原来只编译 `poster.cpp` 和 `test_poster.cpp`。改动后 `poster.cpp` 为了取 `platf::appdata()` 包含了 `platform/common.h`，它带入配置模型、Boost.Log 和协议库的头，所以这个目标链接 `sunshine::host_headers`、`Boost::log`、`Boost::thread`，并带上 `SUNSHINE_DEFINITIONS`。日志器、`appdata()` 和 `path_to_utf8()` 由新增的 `tests/unit/poster_platform_stubs.cpp` 提供，写法沿用 `config_runtime_stubs.cpp`。`appdata()` 指向进程级的 `ScopedTempDir`，缓存落在进程级临时目录里，进程退出时自动删除。每个用例的源文件路径唯一，key 不会互相冲突。

poster 单测：

- 非 ASCII（中文、含空格）源路径。`schedule()` 后用等待函数取到预览，它在 `platf::appdata()` 下的缓存目录里，文件名是纯 ASCII，源目录里只有源文件。
- 源文件被覆盖（大小或 mtime 变化）。key 变化，后台生成新的预览，旧缓存文件仍在。
- 清理函数传入含 `1-preview.jpg.tmp-4242` 的临时目录。临时文件被删，`1-preview.jpg` 保留。
- 清理函数传入 70 个缓存文件（mtime 逐个递增）的临时目录。淘汰 6 个，只剩最新的 64 个。
- 清理函数传入被普通文件占位的路径，以及父路径是普通文件的路径。返回「不可用」，不抛异常。传入不存在的路径时创建它。
- 超过 200 KiB 且无法解码的源（随机字节），未 `schedule()`。`preview()` 返回空，等待函数立即返回空，不等待。
- 超过 200 KiB 的合法源，已 `schedule()`。等待函数返回预览。
- 超过 200 KiB 且无法解码的源，已 `schedule()`。等待函数在工作线程放弃后立即返回空，耗时远小于上限。

`asset` 处理器的返回规则没有路由级单测。`tests/unit/test_asset_https_routes.cpp` 测的是 WebUI 静态资源的 confighttp 路由，Moonlight 取封面的 `/appasset` 处理器依赖 `proc`、`config` 等一大串，没有现成的夹具。对应的三条断言放进下面的人工验证。

人工（Windows，中文名壁纸放在 Downloads）：

1. 换一张中文名 4K 壁纸，用标准 Moonlight 重新打开应用页。桌面封面在 2 秒内出现，响应不超过 200 KiB。
2. Downloads 无新增文件，`config\covers\cache\poster\` 出现 `<key>-preview.*`。
3. 再打开一次应用页。日志没有重建记录，封面立即返回。
4. 换一张 8K PNG，让生成超过 2 秒。第一次打开应用页显示默认封面；客户端重新请求且预览已生成时才显示预览，等生成结束后重新打开应用页应显示预览。
5. 看一个其他应用的封面。标准 Moonlight 拿到的仍是原来的图，预览客户端拿到预览。
6. 预览生成途中用任务管理器结束 Sunshine 进程。重启后首次打开应用页，`.tmp-*` 被清理。
7. #1471 截图里的历史残留文件。设计不处理，手动删除。
8. 抓包确认响应头。预览命中且带 `v` 时是 `public, immutable`，回退默认封面时是 `no-store`，响应体是 `box.png`。其他应用不带 `fsVariant` 的封面请求仍返回原图。
8. 抓包确认响应头。预览命中且带 `v` 时是 `public, immutable` 加 `X-FS-Poster-Variant: preview`，回退默认封面时是 `no-store` 加 `X-FS-Poster-Variant: default`，响应体是 `box.png`。其他应用不带 `fsVariant` 的封面请求仍返回原图。

## 17. 验收标准（对照 #1471）

1. 预览缓存与临时文件只出现在 `platf::appdata()` 的缓存目录。
2. 非 ASCII 壁纸路径的缓存名与命中判断均不乱码。
3. 缓存成功落盘后 #1357 的跳过生效，4K 壁纸不重复解码。
4. 进程启动后清理遗留的 `.tmp-*`，缓存文件数有上限。
5. 带 `fsVariant=preview` 的请求和桌面壁纸的封面请求永不返回超过 200 KiB 的原图，回退响应不被客户端长期保存。
6. 缓存路径上的任何异常与失败不改变主程序与串流行为，请求线程新增的阻塞不超过 2 秒且只在封面请求上。
