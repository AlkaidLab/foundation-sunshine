MAT Android C: explicit RTSP negotiation -> independent IEC61937 session
2026-10-21

RESULT: PASS, no-device scope. Final evidence: C-PROOF.json.

Implemented
-----------
- New codec5 / mat-iec61937-v1, separate from codec4 / mat-dump-v1.
- Host DESCRIBE explicitly advertises the finite replay capability and manifest.
- Client ANNOUNCE explicitly selects playback and echoes carrier, logical clock,
  cycle count and SHA256; host rejects missing/mismatched/mixed profile fields.
- Client requires a matching ANNOUNCE response, with no dump/Opus fallback.
- New profile: carrier=iec61937-192000-8-s16le; logical clock=48000;
  manifest remains bounded to 1..1000 complete cycles. This is not infinite live capture.
- Existing Sunshine RTP send, pacing, FEC and optional encryption are reused.
- common-c codec5 bypasses startup drops and ordinary decoder/PLC callbacks.
  After decrypt/reorder/FEC, MatPlayback owns shared complete-cycle reception
  and input SHA/count verification, with a separate full-cycle consumer callback.
- Actual production JNI delivers the 61,440-byte cycle and epoch/domain/index/PTS
  to MatPlaybackSession -> bounded MatCarrierPlayer -> MatAudioTrackSink on Android.
- EOS input SHA/count must verify before Java drain is requested. Only successful
  drain can return a successful playback EOS. Partial writes and errors do not
  silently drop, conceal, switch codecs or resume in the middle of a cycle.
- Android SmartAudioRenderer routes only negotiated codec5 to MatPassthroughRenderer.
  MAT never enters the 16KB AC3 callback, Opus decode, PCM or audio-haptics analysis.
- JNI setup/cleanup registers and releases the dedicated consumer after audio
  thread lifecycle boundaries; the dump renderer remains lifecycle-only.

Client opt-in
-------------
Settings: enable audio passthrough, explicitly select
"MAT IEC61937 -- finite replay / HDMI (experimental)" in the audio codec list.
Disable the existing MAT dump checkbox if playback is intended. That checkbox
retains its prior precedence and dump-only behavior. Normal auto/Opus/AC3/E-AC3/
PCM behavior is not changed and MAT is never selected automatically.
The host must explicitly configure a replay recording. The installed host was
not reconfigured in this work; test hosts use isolated temporary configuration.

Negative negotiation: negative03/
---------------------------------
Fifteen cases use the ACTUAL production client against a controlled negative
RTSP peer (not a substitute for the separate real-Sunshine positive tests).
Missing/version/carrier/clock/SHA/count/duplicate DESCRIBE capability; wrong
codec/SHA/count/carrier/clock ACK; missing ACK; identical and case-folded duplicate
ACK. All reject in the RTSP handshake, before PLAY and before any carrier bytes.

The negative test found that the old RTSP parser coalesces identical header
names. A parsed duplicate marker now preserves that fact for the new playback
confirmation validator; generic legacy last-value-wins lookup is retained.
Parser-owned duplicate nodes are freed. Codec5 also checks header names without
ASCII case sensitivity. This prevents a duplicate confirmation being mistaken
for one unique, valid confirmation.

No-device limits
----------------
No Android AudioTrack/HAL, TV internal-app route, HDMI/eARC Soundbar, actual
Atmos recognition, rendering or device latency was exercised.
The real Android callbacks adapter is compiled; the Windows harness exercises
the same production JNI delivery and Java session behind its platform adapter.
No full Moonlight APK/native application link, installation or device execution
is claimed. The A/B standalone diagnostic APK is not a network Moonlight client.

The full recording SHA is checked at EOS on the streaming path; this does not
mean the whole recording was buffered/verified before the first output cycle.
Per-cycle transport validation precedes delivery. Existing FNV/checksums and
legacy AES-CBC audio are not claimed to provide authenticated audio transport.
