录制对象片段 → Sunshine 音频 RTP → Moonlight 接收落盘
日期：2026-10-20

结论
====
本机 UDP 回环最小闭环通过。必须先把实验 JOC 变长同步帧做成固定长度，
才能兼容当前 Moonlight 的 4 数据 + 2 校验音频 FEC。直接送变长帧会失败。
传输后，独立解码得到的对象 PCM 与坐标逐字节等同于传输前的候选码流。
这不是安卓真机 Dolby 解码/Atmos 点亮通过，也不是完整 Sunshine 产品集成。

验证范围（非常重要）
==================
1. 输入是已录制的《仁王 3》两个同时非零的动态对象 PCM + XYZ 片段，
   来源 joc-spike/rust02/game-2/expected.npz（更早的 game01 有一路静音，未用）。
   用现有 Rust QMF / unsigned JOC + FFmpeg 640 kbps core 候选重新编码。
2. 先编码完成，再按每帧 32 ms 经 UDP 发出。不是把实时对象采集器已经接入生产。
3. 发端复用仓库真正的 audioBroadcastThread、encode_audio、RS/FEC 以及 Windows
   platf::send/WSASendMsg，不是 Python 重写 RTP。数据经真实 mail::audio_packets 队列。
4. 因当前仓库视频子模块声明/旧构建对象不一致，未声称完整应用重新构建通过。
   build.ps1 从 src/stream.cpp 和 src/platform/windows/misc.cpp 按标记原样机械提取
   上述函数，编入隔离测试程序；独立前端仅提供最小会话状态、日志和录制片段源。
   source-chunks.json 保存规范化换行后的原函数 SHA-256；生成的 C++ 也保留在构建目录。
   原版 crypto.cpp 直接编译；收端用当前仓库 third-party/moonlight-common-c 的
   RtpAudioQueue.c / PlatformCrypto.c 原文件编译，未修改客户端 FEC 或解密器来通过测试。
5. 接收前端是本机 Windows 原生落盘程序，不是 moonlight-vplus APK；未连接安卓设备。
   未覆盖配对、RTSP codec/profile 协商、视频/音频同步、JNI、AudioTrack/MediaCodec。
6. 仅绑定 127.0.0.1 随机端口；没有监听局域网，无需改防火墙。
   没有运行 audiodg 注入、驱动、音频切换、游戏操作、安装/替换 Sunshine 或重启服务。

实际发现的问题和适配
==================
A. 变长帧不能原样接入现有音频 FEC。
   《仁王 3》候选 93 帧长度 2648..2664 B，共 7 种。
   baseline02：明文和 AES 两种都只有 92/93 个内容帧，所有线上的 UDP 包实际收齐；
   Moonlight 输出 Audio block size mismatch 并禁用 FEC，触发失配的一个帧没有交付。
   明文示例 got 2662 / expected 2664；AES 示例 got 2656 / expected 2672。
   所以不能只把带 JOC 的 AVPacket 塞进现有队列就认为端到端完成。

B. 本轮研究适配：每个 E-AC3 同步帧固定为 3360 B。
   run.py 的 fixed_frame 在帧内部、尾部标志之前插入零填充，修改 frmsiz、重算 CRC16。
   不修改 JOC/OAMD、音频数据、不追加自定义 RTP 尾巴、不让接收端猜长度/裁零。
   仅支持已验证的 unsigned skip-field、auxdatae=0 片段；超预算、奇数长度、CRC 错误拒绝。
   这是实验帧整形器，还未并入 Rust 的生产 ABI 或 Sunshine 编码线程。
   3360 B / 32 ms = 840 kbps 码流；AES 后 3376 B，再加约 50% FEC 与 UDP/RTP 开销。
   对两个对象的片段，固定预算增加了带宽；更优的分组/协商协议仍需后续设计。

C. Moonlight 原接收队列有启动同步：故意舍弃第一个 4 包 FEC 组。
   测试显式先发 4 个预热帧（128 ms），再发送完整的 93/96 个内容帧。
   接收队列逻辑未绕过。内容首包 seq=4、timestamp=128；后续每帧 timestamp +=32。
   此协议的音频时间戳单位是 ms，不能直接改成每包 +1536。
   完整 AudioStream 的其他启动丢弃逻辑并未运行，不应据此承诺真实应用启动延迟。

实测结果
========
game-pass02：录制《仁王 3》2 对象，93 帧，2.976 秒。
  明文：无故障 / 交换相邻数据包 / 每 4 数据包丢 1 / 每 4 数据包丢 2，全通过。
  AES： 同上四组，全通过。
  每一组均 93/93，序号/时间戳/帧边界无错误，FEC 未禁用，无 concealment。
  丢 1 恢复 23 个数据包；丢 2 恢复 46 个；两份校验包均保留。
  所有结果与 sent.eac3 的 SHA-256 完全相同：
  acf803c1733ad95e8a1b74c27f15aa00b8b6076afc65d2b79db39d4b898b149d

tone20-pass01：20 对象合成压力片段，96 帧，3.072 秒。
  原变长码流 3230..3312 B，共 37 种长度；整形后同为 3360 B。
  明文 / AES，各自无故障与每 4 数据包丢 2，共四组全部通过。
  每组 96/96；受控丢包组恢复 48 个数据包，FEC 未禁用。
  所有接收结果 SHA-256：
  74e6ceca9c714d1dd6dc2ac0c3806f36f985c89674a46e8da3bd2bac4199b998

独立解码与内容保留
================
game-pass02：Cavern 请求 90 帧（留出解码器尾部 lookahead），90/90 成功，2 动态 + 静音 LFE。
tone20-pass01：Cavern 请求 93 帧，93/93 成功，20 动态 + 静音 LFE。
两组均将原始未整形候选与接收落盘候选独立解码比较：
  所有 object-XX.f32 文件、positions.csv，文件哈希逐个相同。
  FFmpeg 对原始/整形/接收三者严格 core CRC/bitstream 检查通过，PCM 哈希相同。
说明帧内填充和 RTP/FEC/AES 没有进一步改变已编码的对象音频与坐标。
不说明候选编码器相对原始 PCM 无损，也不说明 Dolby 商业解码器接受 unsigned 元数据。
《仁王 3》坐标轨迹变化次数 16 / 12，量化位置误差与先前相同；
对应原始对象的相关系数约 0.999616 / 0.999703，原有编码重建误差并未消失。
20 对象宽带同时重叠的串扰问题没有被本轮网络验证解决。

网络与安全边界
==============
最大 UDP payload：明文 FEC 3384 B，AES FEC 3400 B，低于当前 native 4096 B 接收缓存。
测试前端显式预留一个完整 AES 额外填充块；3360 B 测试本身也在现有生产缓冲预算内。
这不代表生产 session::alloc 的所有最大帧边界已修复或验证。
但超过常见以太网 MTU，真实 LAN 可能依赖 IP 分片；本机回环不证明 Wi-Fi/WAN 可靠性。
受控丢包/乱序在落盘前端、调用原 Moonlight 队列之前执行。不是随机公网丢包保证。
3360 B 并非未来所有对象/元数据场景都够；更大帧须显式扩大/协商预算并检查 AES 额外块，
不可照搬本轮结论发送 4096 B 帧或忽略现有分片问题。
仅使用公开的固定测试 AES key 00..0f 与 keyId 0x10203040；不读取真实配对凭证。
没有提取 Dolby 密钥、修改认证/保护逻辑或修改设备能力来模拟点亮。

重现（仓库根目录，PowerShell 7 + Python 3.11 / NumPy）
===================================================
构建脚本依赖本机现有 build/dlssnr-host 配置、MSYS2 UCRT 工具链与库，不是跨机安装器。
每次输出目录须不存在，旧结果不会被覆盖。

  pwsh -File ./spatial-object-spike/rtp-spike/build.ps1 -Output ./spatial-object-spike/rtp-spike/build-new
  C:/Python311/python.exe -B -u ./spatial-object-spike/rtp-spike/test_framing.py

从已录制对象重新编码并走网络：
  C:/Python311/python.exe -B -u ./spatial-object-spike/rtp-spike/run.py --build ./spatial-object-spike/rtp-spike/build-new --output ./spatial-object-spike/rtp-spike/game-new --frame-bytes 3360 --modes plain aes --faults none reorder drop1 drop2 --decode

不带 --frame-bytes 3360 可重现变长帧负例（预期退出码 1）；
--encoded ./spatial-object-spike/rtp-spike/game-encoded01 可复用本轮重新编码结果。
--fixture tone20 --frames 96 可跑 20 对象压力组。
输出含 sent.eac3、wire-source.eac3（另含预热）、每组 received.eac3、frames.csv、stats.json、
sender/receiver 日志、summary.json，以及 --decode 的 core/对象/坐标对比。

下一步
======
1. 将固定帧预算放进 Rust 注入器，或设计显式长度且双方协商的新 FEC profile；
   不要改变所有普通 E-AC3 客户端的默认行为。
2. 接入 Sunshine 显式实验配置：对象源 → 同步/状态缓存 → core+JOC 编码 → 现有音频队列。
   生产缓冲区、队列时钟、分片和 EOF/丢失处理必须另外校验。
3. 在 moonlight-vplus 原生接收回调增加可关闭的落盘探针，跑安卓真机 RTP/RTSP；
   然后独立验证系统 Dolby 本机解码/Spatializer/实际输出，不能以本报告替代。
4. 开源候选与 Cavern 的非商用/共享条款仍适用；本轮没有解决正式分发授权。
