2026-10-21（Asia/Hong_Kong）

结果
----
完成 Windows x64 固定布局共享内存协议与两个自有进程的回放测试。
生产者 100 Hz 目标送料 -> 共享内存 32 槽 -> 接收进程 -> 原有 8 槽独立编码线程。
接收端使用假编码器，未加载 Dolby，也未访问 audiodg、游戏或音频设备。

正常/延迟两种模式各回放两个域，共四段完整回放全部通过。
消费线程实际收到的 PCM、XYZ、对象控制与 Process 序列，可重组为此前真实 MAT
短测的完整输入，逐字节相同，源导出（含 EOF）也逐字节相同。
新增 20 项协议测试，加原有 65 项，共 85 项；最终构建重复 10 轮，850 次检查通过。
另有 14 类真正双进程异常测试通过，测试进程全部退出，无强杀或自动无限重试。

范围限制
--------
这是两个同一用户普通进程间的离线验证，不是 audiodg/PPL/跨令牌权限验证。
没有 UAC、注入、真实 native 编码、驱动、端点、安全设置或系统全局计时精度变化。
没有修改既有冻结桥接/队列/原生探针及其输入，也没有修改生产默认链路。
未新增认证 MAT 解码、编码后 XYZ 标定、元数据/音频精确同步或 Android Atmos 验证。
*-fake-plan.bin 为假接口调用记录，不是 MAT 码流。

协议 v1（私有、当前 Windows x64 ABI，非网络格式）
----------------------------------------------
共享区只放固定宽度字段和原生数组，没有指针、Boost 队列对象、mutex 或堆容器。
  Contract：128 字节
  槽位区域偏移：320 字节
  Message 固定头：80 字节
  WireCall：1,952 字节（ID/slot/type/flags/XYZ/frame count/480 个 F32）
  每槽：125,056 字节，最多 64 个调用（包含 end 控制余量）
  有效槽：32；映射总大小：4,002,112 字节
  接收进程的原有 8 槽队列另外占 1,124,784 字节
两者共 5,126,896 字节，另有少量在途快照及 worker 状态；不是总进程内存。
离线输入预加载与假接口全量记录会随片段增长，不是常驻实现的内存结论。

Contract 校验：magic/version、头/映射/槽/调用尺寸、容量、48 kHz/480 frames、
QPC 频率、保留字段、domain、epoch、128 位随机 nonce 和生产者 PID。
接收端还用继承的进程句柄核对生产者 PID + 创建时间，防止只靠复用后的 PID。
消费者 PID 用一次 Interlocked CAS 绑定，生产者与实际创建的子进程 ID 再核对。
连接后继续检查不可变 Contract；修改后不继续使用旧流。

Message 校验：长度/调用数/类型、domain/epoch、单调消息序号、保留字段、
入队时间和 FNV-1a 校验值，检查通过后才按有界长度复制 PCM。
校验值用于偶发损坏检查，不是密码学认证，也不是防恶意同用户进程的安全证明。
业务调用类型、非有限 PCM/XYZ 和对象生命周期继续由既有 Pipeline 验证。

SPSC 规则：
  单生产者/单消费者；按写/读计数取环形槽。
  先写完完整消息，再用 Interlocked 更新写计数发布。
  消费者先检查并复制到自有快照，再用 Interlocked 更新读计数。
  控制与计数器按 64 字节对齐，不依赖跨进程 std::atomic::wait 或进程内指针。
  生产者一次尝试，无容量等待/重试；满队列使 epoch 失败，不覆盖或跳帧。
  读写计数损坏在索引前拒绝；单测含 1,000 帧环回，实际回放也跨越多次环回。

连接与权限
----------
创建匿名映射与事件，没有可猜名字的 Global 对象，不改对象/系统的权限设置。
CreateProcess 使用 CREATE_NO_WINDOW 和明确的 HANDLE_LIST，只继承五个句柄：
映射、数据事件、取消事件、就绪事件、生产者存活/身份查询句柄。
句柄是当前测试父进程拥有并授权给自己创建的子进程；没有附加或打开外部音频进程。
此连接方式不能直接等同于向已存在的 audiodg 交付句柄，后者仍需另行设计与授权。

EOF / 失败 / 存活
----------------
EOF 是单独的控制消息；producerDone 只表明发布结束，不允许代替 EOF。
处理 empty 与最终发布竞态：观察 done 后再次读取发布计数，不能漏掉最后一包。
EOF 不推进源 Process 或样本时钟；尾部控制进入原有明确的 30 轮 drain。
丢失 EOF、坏序号、坏身份、校验损坏或溢出均失败，不伪造静音补洞。

约 20 ms 控制线程更新进程心跳，超时阈值 1 秒；OS 进程句柄同时检查对端退出。
这是进程/控制面存活检查，不代表真实 vendor 调用一定有进展。
等待期间生产者继续心跳，防止编码器排尾被误报为生产者失联。
首个失败原因保留；失败输出不可作为完整流播放或与下一 epoch 拼接。
重建必须建立新映射/新 epoch，不在活跃共享区里清零重置。
未来真实 vendor 调用若阻塞，本协议不能安全抢占它；不存在强杀 audiodg 的逻辑。

双进程完整回放（最终 proof02）
----------------------------
每种模式均独立重建两个域，使用不同 epoch：
  正常：domain 1 / epoch 1001；domain 2 / epoch 1002
  延迟：domain 1 / epoch 1101；domain 2 / epoch 1102
每次生产者与接收者 PID 不同，映射和对象状态独立。

每种模式的两域合计：
  512 个源 Process 轮 + 40 预热 + 60 drain = 612 个假 Process 调用
  863 次对象提交；384,000 原始单声道样本
  514 个 IPC 消息 = 512 个源轮 + 各域 1 个 EOF
  源消息无拒绝、无容量重试；生产者不受队列容量背压
  write == read == accepted == received，各域分别为 307 / 207
完整重组输入 SHA256：
  ae4c5525ce885670227ae960d0a34d54fe017220fd934b5f78463f432903b089
与 mat-native-v4-input01/input.bin 相同；本轮未重新执行那次真实原生编码。

短测墙钟观察，不是 CPU/硬实时/真实编码或播放延迟：
  正常：共享环高水位 12/32，编码队列 8/8；中位延迟约 200.6 / 200.1 ms
  延迟：每域初始化等待 60 ms，源第 60 轮另停顿 40 ms；共享环 25/32、21/32；
        中位延迟约 286.2 / 285.2 ms，最大约 332.9 / 295.2 ms
  延迟为“生产者入共享区 -> 假 Process 完成”，不是声音播放端到端延迟。
  两端仍使用线程自有高精度等待计时器；落后时重定位，不无限突发追赶。
  约 200 ms 预热库存仍保留，跨进程化没有解决交互串流的低延迟障碍。

14 类双进程异常（均预期失败并退出）
----------------------------------
  初始协议版本错；连接后 Contract 被改；会话 nonce 错；帧 epoch 错；
  帧长度错；校验值错；消息序号错；32 槽满后第 33 次入队；显式取消；
  生产者自行 ExitProcess(23)；接收者自行 ExitProcess(31)；
  生产者仍活但心跳停更；接收者仍活但心跳停更；缺失 EOF。
初始身份/版本失败在假编码器打开前拒绝。
坏消息夹具在发布计数前构造，不依赖修改已发布槽的竞态。
异常退出只发生于本轮创建的自有测试进程；Python harness 不调用强杀/terminate。
生产者异常退出后，接收者通过 OS 存活句柄失败并自行退出。
harness 按记录的 PID + 创建时间审计接收者退出，不对无关进程操作。
