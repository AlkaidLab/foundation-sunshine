MAT 主机侧 spike / 2026-10-20
============================

结论
----
主机已有的原生 MAT-family 录制数据不是空载波：在启动的三个尚未匹配研究布局的周期
之后，可以解出两个独立动态 PCM 槽和随时间变化的对象字段。无需先经过自制 JOC 下混/
重建算法。原始载波还能分为 MTU 内的小包，经本机 UDP/RTP 回环后逐字节恢复。

但没有安卓真机连接，尚未验证系统 MAT 解码器、本机扬声器/耳机输出或 Atmos 点亮。
不能把当前结果写成 MAT 完整端到端已通过，亦未实现完整 Sunshine/Moonlight 集成。
用户已选择稍后连接安卓设备，本轮明确只验证主机侧。

输入与安全边界
--------------
使用原有 resident/encoded01/encoder-output.bin / encoder-payload.raw。
这是 2026-10-18 在默认 F32D80U / Dolby Home Theater 路由、受控 spatial_probe 源下录制的：
两动态对象，频率分别 523.25 和 783.99 Hz，持续 5 秒；不是《仁王 3》或新游戏测试。
当时的 encoded_tap 取的是 audioeng 的原生编码器输出，未通过虚拟驱动取得。
本轮没有重新注入 audiodg、播放音频、启动游戏、切换端点/空间音效或重启音频服务。
未安装驱动、修改 EDID/注册表/根证书/签名策略，也未提取或调用厂商私有 codec DLL。
ADB 只启动了标准主机 daemon，并两次确认设备列表为空；未安装 APK。

载波完整性与观察到的格式
----------------------
506 条编码回调，每条 480 输入样本、30720 输出字节；旧采集报告 drops/invalid/failures=0，
status=2/error=0，钩子原字节恢复成功。重新读取记录，序号、长度、QPC 单调及旧提取逐字节吻合。
总载波 15,544,320 字节，253 个 IEC61937 周期，各 61,440 字节；Pc 低 5 位均为 0x16。
音频时钟为 242,880 / 48,000 = 5.06 秒（包含原生编码器启动/尾部）；每秒 50 个周期，
载波为 24.576 Mbps。不要误用原采集器 10.078 秒的墙钟运行窗口计算码率。

源载波 SHA-256：
38578e66d5853e8cf4ddb756f46a92a236e79e496a88a6cd28a3ff33bfd00094

每对 16 位传输字节交换后，逻辑头为 079e0008 / 079e0009；它不是普通 TrueHD-in-MAT
起始序列。Pc=0x16 本身不足以进一步判定具体 MAT profile 或证明 Dolby 格式合规。
MAT 的 Pd 在本次检查中按字节长度处理，不沿用普通 AC3 的位长度规则。

Python analyze_mat.py 和原样 C++ mat_format.cpp 的结果：
  250 个周期匹配完整的观察布局；最初 0/1/2 三周期不匹配，保留但不伪造 PCM/对象。
  每周期两半，每半 10 ms：31 个全频 PCM16 / 48 kHz 槽，加一个独立 12 kHz LFE 槽。
  按该公开研究的解释，前 11 个全频槽为静态槽，后 20 个为动态槽。
  本样本只有全频槽 11 / 12 非零，分别匹配 523.25 / 783.99 Hz 测试源。
  其余静态/动态槽和 LFE 为零。没有把载波的 8 个物理通道当作游戏 7.1 声道播放。
  提取的 31 槽 PCM 共 240,000 帧，两套实现全部字节相同。
  PCM SHA-256：3f9d6bf7abbc5b8e60e55dfdd0f6bceca3f2281225d6c632d8407107caf55dab
  500 个半周期 x 20 对象 = 10,000 行六字段记录，两套实现逐个整数相同。

对象字段能说明什么
------------------
本轮提取每动态槽六个 6-bit 字段，不擅自命名为原始 Windows 米制 XYZ。
参考研究将前三字段解释为 X / Z / Y 控制值，并指出经过了感知变换，不是线性米制坐标。
本样本动态槽 0 的前三字段变化次数为 93 / 125 / 12；槽 1 为 101 / 114 / 12。
后面三个字段在样本中保持 4 / 3 / 31。其余十八个动态槽保持默认值且 PCM 为零。
这验证了音频槽与变化字段都存在，尚未独立校准坐标变换、增益语义或每个游戏对象 ID。
PCM 也可能已有上游音量处理/量化，不声称与原始 float 游戏对象逐样本无损相等。

FFmpeg 控制实验
----------------
本机 FFmpeg 7.1 有 truehd/mlp/eac3 decoder 和 spdif demuxer，但直接尝试解码旧载波失败，
日志明确为 Data type 0x0016 in IEC 61937 is not implemented。
对应公开 FFmpeg 7.1 源码的 spdif_get_offset_and_codec 未支持这个数据类型。
查询当日 master 的同一 switch 亦未发现 MAT 项。这不代表载波坏了或 MAT 不可解码；
仅说明不能把我们现有的 FFmpeg E-AC3 解码能力直接当成 MAT PCM/object 解码能力。
反过来，FFmpeg 为 TrueHD 输出做 MAT 封装也不等于能把对象 PCM/坐标编码成 MAT 2.x。
https://raw.githubusercontent.com/FFmpeg/FFmpeg/n7.1/libavformat/spdifdec.c
https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/libavformat/spdifdec.c

网络可行性测试（不是现有 Sunshine 音频协议）
-----------------------------------------
transport_probe.py 使用私人实验 PT=110 的 RTP 头和 MATS 分片描述符，本机 127.0.0.1。
253 周期完整发送，每个 61,440 字节周期分为 53 包，总共 13,409 包。
UDP payload <=1200 字节，IPv4 无选项时 IP 包 <=1228 字节；不依赖常见 1500 MTU 的 IP 分片。
刻意将每个周期的所有分片逆序发送；接收侧有 8 周期缓存上限、长度/重复冲突和 CRC32 检查。
253/253 周期重组成功，0 错误/0 未完成周期，整载波 SHA-256 与源完全相同。
RTP+分片头的 UDP payload 码率约 25.2544 Mbps，尚未加 UDP/IP/L2、加密或 FEC 开销。

测试记录的组装延迟中位数约 1.09 ms / P99 1.86 ms，但只是同进程 Python 本机调度：
排除了生成/捕获、20 ms 周期填充、终端解码/渲染，不是游戏声学端到端延迟。
这轮没有网络丢包恢复或加密；CRC32 不是认证。不能承诺实际 Wi-Fi/WAN 稳定性。
测试协议未接入 Sunshine、未协商 RTSP、未改 Moonlight，不能拿旧 EAC3 队列直接发送 MAT。

路线判断
--------
值得保留“Windows 原生 MAT 捕获 → 分片传输 → 设备原生 MAT 解码”作为独立候选。
主机原生编码已存在，避免了从对象自行生成 JOC/重建对象，也保留整段上游 MAT 字节。
当前仍依赖原 Windows Dolby 空间提供程序及原验证端点条件；没有实现无端点的 MAT 生成器。
这不是从任意录制对象 NPZ 直接生成合规 MAT 的证据，也不说明所有游戏均能捕获。
最终是否优于 JOC，取决于安卓本机入口、带宽预算、实际游戏覆盖和端到端延迟。
