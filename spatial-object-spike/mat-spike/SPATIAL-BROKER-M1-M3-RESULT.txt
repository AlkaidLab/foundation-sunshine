M1验收
------
直接读上次真实原生输出encoder-payload.raw，每次只持有一个61440字节周期。
178帧，10936320字节，含全部启动阶段原始字节，回放逐字节一致：
  79cd69e33adcd1bcffe95673564b6fc727a7aaed7370745d43ec269925a492f6
残缺周期、坏前导和空文件均拒绝。源是单会话，不隐式重启/重用epoch。
格式明确是MAT IEC61937载波，不冒充E-AC3或裸MAT。
时间戳是48kHz逻辑载波时钟，每周期960帧；未标定为原游戏媒体PTS，未隐藏200ms库存。

M2验收（每轮验证）
------------------
实际链路：
  自有MSVC进程读取冻结原始录制 -> MSVC q4::Ring ->
  自有GCC子进程内的MSVC C ABI reader DLL -> ObjectBroker ->
  旧Assembler/DomainBridge -> 新DLL输入环/内部8槽 -> 假codec工作线程 ->
  编码输出8槽 -> 独立消费线程。

文件只作冻结输入和测试结果旁路，reader、bridge和codec之间没有文件中转。
真实环仅由MSVC解释，C ABI参数40字节、事件缓冲8368字节，在两编译器端实测一致。
子进程仅显式继承mapping/owner/ready三个句柄，CREATE_NO_WINDOW。
Reader复制头和PCM到caller-owned缓冲后才推进read；空闲poll也维护采集心跳。

normal：一遍录制，两域；paced：假codec按10ms节拍，两域；
wrap：录制重复5次，10域；idle：先不发布数据验证心跳，再回放两域。
合计16次完整单域回放。每个两域集合包含512源轮、612 Process、
863 Submit、384000源样本。两轮最终验证共32次完整域回放。
5次重复的采集事件数15700，4096槽输入环实际回绕3次。

所有桥接帧与冻结MATBRG1文件体一致；首遍连QPC字段也逐字节一致。
重复录制只改观察域/全局序号/QPC以维持合法新流；比较时只规范化这些QPC字段，
未改变PCM、XYZ、对象身份/生命周期或源Process计数。
所有假Submit/Process转录逐字节等于已原生验证的MATV4P1输入计划。
对象增益仍按原F32顺序只施加一次，后续Submit的volume/gain保持1。
分卷不重置状态；显式域关闭清理缓存/桥接，EOF不增加源Process。
桥接身份历史及时释放，已关闭域不长期保留容器。

6种采集失败场景拒绝：协议版本、owner创建时间、loss epoch、序号缺口、
缺DomainEnd、owner自有测试进程主动退出。最后一项由fixture自己ExitProcess(23)，
不是强杀其他进程；退出后reader失败，子进程正常以失败码结束。
另测未选择域不进入编码器，以及显式encoder身份排除（排除域1、保留域2）。
这些身份筛选测试不能证明真实采集hook与自建编码器已可共存。

M3验收（每轮验证）
------------------
新输出映射994752字节，固定8槽，与输入时长无关；不是整个代理内存占用。
每槽80字节头，带format/epoch/domain/sequence/载波样本游标/phase/sourceIndex/
完成QPC/长度/校验。Native有效载荷最多30720字节；较大槽容量用于明确标记的
diagnostic_call_plan，绝不作为可播放MAT交给EncodedAudioSource。

核心环执行100000次发布/复制/消费，等价12500轮8槽复用，无字节变化。
统计字段与输出序号越过UINT32边界测试通过，不再被4GB字节计数截断。
新DLL连续假接口实测1200源轮+20预热+30排尾=1250 Process，
1220 Submit、575520源样本、输出环复用156轮；整份转录由Python独立重建逐字节匹配。
已实际越过旧350源轮/400总轮上限，不是只改常量后编译。

新DLL实测7项失败：初始化S_FALSE、Submit E_ABORT、Process S_FALSE、过量输出、
输出消费者停读、消费者取消、普通宿主调用native入口被守卫拒绝。
所有已创建工作线程都正常返回、workerTimedOut=false。native守卫在vendor之前拒绝。
另有10项环/source单测：回绕、满环不覆盖、坏校验、fake不能标成MAT、半块聚合、
残缺EOF、epoch不符、取消分类、原生奇数半载波排尾策略、64位计数。

原生输出容量等待预算20ms，仅在codec线程；capture callback永不等待。
未节拍的FAKE离线模式单独允许1秒等待，以容纳测试文件I/O/调度；不能拿这个
较宽预算声称真实低延迟背压验证通过。满环超预算会终止epoch，不覆盖/静默丢包。
Native严格要求本机已验证的30720字节Process产量；奇数半载波结束时额外一轮
静音drain闭合61440字节周期，不增加源轮、不裁音频。新native策略仅单测/编译，
本轮未调用真实编码器，后续原生验证仍必须明确检查它。

实现中发现并修正的两项问题
------------------------
未节拍FAKE全速输出在严格20ms预算下可能因诊断写盘调度而触发真实满环停止；
没有放宽生产native预算，而是把1秒预算限定在显式FAKE未节拍测试模式。
独立验证还发现取消与发布并发会被误记为overflow，现已分别传播cancelled/counters/
overflow，并保留原始首错；最终两轮完整验证都通过。
中间build01..06及proof01失败/proof02较早成功证据保留；最终以build07/proof03/04为准。

未覆盖范围与后续接口
------------------
本批不包含生产代理守护进程、broker RPC服务端、安装/服务化或自动部署启动。
C ABI reader接收已提供的合法采集mapping；真实hook准备/安装仍需受控宿主接入。
Native接收器单宿主只允许一个活动编码会话；线上首版必须显式选域，不能直接
把多个同时活动域混合。这里的两域录制按顺序关闭/重建，不证明并发多域混音。
动态对象合同仍限480帧全跨度、最多20个存活对象；静态bed、短包未知offset、
一般游戏输入、中途启动完整状态、端点切换、版本升级与长时间soak仍需各自验收。
未知坐标不伪填零，沿用原桥接的隔离规则；不能声称覆盖任意游戏的全部声音。

没有实现RTP分片/加密/FEC、客户端重组或Android renderer，留给M4及设备验收。
200ms预热库存仍在；未证明原始媒体PTS对齐、CPU开销、实时截止时间或低延迟。
新native分支的真实连续编码、实际采集与自建编码共存、阻塞vendor保留状态，
均没有用这轮自有普通进程FAKE测试冒充通过。
