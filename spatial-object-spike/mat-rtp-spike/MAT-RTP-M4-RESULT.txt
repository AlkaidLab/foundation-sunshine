M4：已验证 MAT 录制 → Sunshine RTP → Moonlight 重组落盘
======================================================

范围与结论
----------
本轮实现的是 M4 的“回放传输验收”子阶段：复用 M1 的 MatReplaySource，
把既有原生 MAT 录制分片，经 Sunshine 实际音频广播函数、AES、4+2 FEC、
Windows UDP send 发出；原生 Moonlight 接收端排序/FEC/解密后重组并落盘。
不是 Python 模拟网络协议，也没有把 E-AC3 当 MAT 发送。

验收数据：
  spatial-object-spike/mat-spike/mat-native-session-run02/capture/encoder-payload.raw
  10,936,320 bytes = 178 × 61,440-byte carrier cycles
  carrier timeline：178 × 20 ms = 3.56 s，包含全部启动/排空数据。
  原始与成功落盘文件 SHA256：
  79cd69e33adcd1bcffe95673564b6fc727a7aaed7370745d43ec269925a492f6

本轮未进入 audiodg、未编码、未弹 UAC、未改端点或安全设置、未安装驱动、
未启动游戏、未部署服务。M1/M2/M3 冻结源码 hash 仍全部一致。

代码接线
--------
src/spatial_audio/MatReplaySource（实际文件名 mat_replay_source.h）
  → src/spatial_transport/mat_fragmenter.h
  → mail::audio_packets
  → src/stream.cpp::audioBroadcastThread
  → 原 encode_audio AES-CBC / reed_solomon_encode 4+2 / platf::send
  → third-party/moonlight-common-c/src/RtpAudioQueue.c
  → 原 PlatformCrypto.c::PltDecryptMessage
  → 新 MatDepacketizer.c
  → *.raw.partial → EOS + 周期数 + SHA256 全部匹配才重命名为 *.raw。

src/stream_mat_replay.inc 是显式实验入口；不接正常音频捕获、不启动 RTSP。
实际广播函数仅加编译期开关内的完成 ACK；正常构建不执行此逻辑。
因为原 audio_packets 队列到 32 项会清空，实验发送端限制最多一个分片在途，
等待实际广播迭代完成 ACK，不能一次向旧队列塞入 60 片。
回放按每周期 20 ms、每片约 333 us 的目标节拍发送；这不是长期实时性能验收。

build 脚本机械抽取真实广播、加密、Windows 地址/优先级/send 函数，记录
source-chunks.json；只有会话状态/启动入口隔离，不重写上述算法。
此仓库整应用视频依赖不完整，本轮没有声称 sunshine.exe 整应用构建通过。

协议 v1（仅显式 dump profile；尚未成为正式 codec/SDP 协商）
-----------------------------------------------------------
共享定义唯一来源：third-party/moonlight-common-c/src/MatWire.h。
主机 mat_wire.h 仅转引；客户端模块无需依赖主机的 C++ 代码。

每个 MAT 载波周期固定 61,440 bytes，切成 60 × 1,024 bytes。
每片额外 80-byte SMAT 头；固定明文长度 1,104 bytes，零填充控制包。
头包含版本、DATA/SYNC/END、格式、时钟、epoch/domain、64-bit carrier序号、
carrier sample_start/rate/duration、分片编号/数量、长度和校验值。
只有 MAT IEC carrier/48k carrier clock 被接受；所有整数显式 little endian。

头字段偏移：
  0 magic(4), 4 version(1), 5 kind(1), 6 headerBytes(2)
  8 format(4), 12 clock(4), 16 epoch(8), 24 domain(8)
  32 frame(8), 40 sample_start(8), 48 rate(4), 52 duration(4)
  56 frameBytes(4), 60 fragmentIndex(2), 62 fragmentCount(2)
  64 bodyBytes(4), 68 frameHash/END streamHash(4), 72 packetHash(4), 76 reserved(4)
  80..1103 body(1024)

SYNC 4 包供原 Moonlight 队列同步丢弃；不是丢弃 MAT 启动载波。
完整 MAT 第一字节起全部发送。END 冗余 4 包，包含总周期数和累计内容校验。
END 重复可接受；缺 END 即使 SHA 一样也不发布完整文件。
固定包长让现有 4+2 FEC 对密文工作，不会遇到可变长度 shard 的问题。
最大 UDP payload（含 RTP/FEC 头）：明文 1,128 bytes，AES 1,144 bytes。

旧音频 RTP 时间戳按 packetDuration 累加且 FEC 用它推导分片时间戳。
实验 profile 使用每片 +1 的合成 transport tick；它不是音频播放时间！
真实载波时钟在 SMAT 头：48,000 Hz / 960 samples，每片同一 frame 的 PTS 相同。
这仍不是已校准的原始游戏媒体 PTS，不掩盖此前编码器启动缓冲。

当前接收策略是 dump-only、严格连续：
  重排/网络重复先由原 RTP 队列处理；depacketizer 也支持同一周期逆序/相同重复片。
  只保留一个 61,440-byte 重组缓存，x64 state 为 61,512 bytes。
  不按线上 frameBytes/count 分配内存；固定上限，先校验再索引。
  缺片/跨周期跳跃/epoch变化/不支持的头/校验错误/IO失败会黏性失败。
  不插静音、不生成“看起来成功”的缺损 MAT；.partial 仅供诊断，不交给解码器。
  不支持跨周期乱序绕过 RTP 队列，也没有丢失重传或动态重同步播放策略。

安全与会话限制：
  所有测试只绑定 127.0.0.1；AES 使用公开固定测试 key，不使用真实配对密钥。
  沿用旧 AES-CBC，没有认证；FNV 只检出意外损坏，不是 MAC。
  SHA256 来自可信本地 fixture 清单，在客户端完成校验后才发布文件。
  旧 IV 依赖 16-bit RTP sequence；本回放入口硬限制 1..1000 周期（≤20 s），
  包括 SYNC/END 不回绕。不能直接拿此测试 profile 当长期加密协议。
  正式版本需密钥/会话生命周期、回绕/rekey 与显式协商设计。

验收证据
--------
最终构建：build05/manifest.json、source-chunks.json。
最终 MAT 验收：proof04/proof.json（20 cases）。
最终既有 E-AC3 回归：legacy02/proof.json（4 cases）。

成功矩阵：plain、AES 各测 none / reorder / duplicate / drop1 / drop2，共 10 组。
每组输入 178 周期；10 组输出大小、SHA256、周期数完全一致；errors/concealed=0。
drop1 是每个有效数据 FEC 组固定丢 1 片，恢复 2,670 片；
drop2 是每组固定丢 2 片，恢复 5,340 片。不是随机公网丢包性能承诺。
每次实际收到 16,032 个 UDP 包，含 10,688 data/control 包和 5,344 parity 包。

失败矩阵：plain、AES 各测 drop3 / dropframe / noend / corrupt / wrongsha，共 10 组。
全部明确失败、不生成 received.raw，保留 received.raw.partial。
特别是 noend：完整内容 SHA 已一致，但缺 EOS 仍拒绝发布。
wrongsha：内容/EOS 完整，但与可信期望 SHA 不符仍拒绝发布。

单元测试覆盖：周期内逆序与相同重复片、重复 END、END 后 DATA、缺片/缺周期、
21 处头变异、空指针/长度、包/帧/累计校验、epoch变化、零身份和写入失败。
E-AC3 回归：新 sender 二进制走旧入口，配旧 build08 Moonlight receiver：
plain-none、aes-none、aes-reorder、aes-drop2 共 4 组均字节相同。

复现（仓库根目录；PowerShell 7；所有输出必须新目录）
--------------------------------------------------
  & ./spatial-object-spike/mat-rtp-spike/build.ps1 -Output ABSOLUTE_NEW_BUILD
  python ./spatial-object-spike/mat-rtp-spike/verify.py --build ABSOLUTE_NEW_BUILD --out ABSOLUTE_NEW_PROOF --suite all
  python ./spatial-object-spike/mat-rtp-spike/regression.py --build ABSOLUTE_NEW_BUILD --out ABSOLUTE_NEW_LEGACY

依赖现有 build/dlssnr-host compile_commands/link flags、MSYS2 UCRT64 GCC、
旧 RTP 前置文件与 nanors 对象。输出含 .exe/.dll、source-chunks 和 manifest。
脚本超时报告 PID 停止编排，不强杀/重试原生探针；测试不需要管理员权限。

尚未完成，不能混为一谈
--------------------

   MatWire.h / MatDepacketizer.h/.c 是可移植 C 模块，但未接 Android.mk/JNI。

   不允许普通 Moonlight 把 SMAT 当 Opus/E-AC3 解码。
3. 未把新实时 broker/编码线程接到此入口，也没有新 audiodg 采集并跑。
4. SHA 一致证明网络透明传输保留所有比特；不证明安卓本机解码点亮 Atmos、
   Dolby 兼容性、坐标语义或端到端播放延迟。那些需要独立设备/解码验收。

建议下一阶段：先加显式 mat-dump-v1 能力协商及 Android 原生 dump 接线，
继续保持 dump-only；然后以同一 Frame 接口替换回放源为真实 broker 输出。
MAT decoder/renderer 和长期加密会话机制应单独验收，不能由此次 hash 替代。
